# Subsystem Deep-Dives

Architecture mechanics that don't change what Claude does in a typical session but matter when working *in* a given subsystem. `CLAUDE.md` carries a one-line summary of each; the detail lives here. Per-file annotations are in `module-reference.md`.

---

## Provider-aware chat sessions

Telegram, cockpit Home, and product chat all enter through `askChatWithContext()` (`src/ai/chat.ts`). It resolves the session's selected alias through `policies/model-policy.json` and delegates to `askClaudeWithContext` or `runCodex`; the transport handler does not choose a provider itself. `DEFAULT_CHAT_MODEL` and `CONVERSATION_MODEL` are `gpt-5.6-terra`, while Claude-only one-shots, agents, and session summarization retain Claude aliases.

Each persisted `Session` keeps Rune's public `sessionId` plus optional executor metadata. Claude bindings store `{format:'claude', sessionId?}`; Codex bindings record `authority` (`read-only`, `product-workspace-write`, or `product-full-access`), the effective cwd, and the scoped writable root. New sessions begin unbound. Restored records that predate executor metadata migrate to Claude using the legacy Rune session id. Explicit legacy Codex `writeEnabled:true/false` records normalize to full-access/read-only respectively (legacy read-only records also normalize their omitted cwd to the vault); legacy metadata never implies fallback workspace authority, and records with no posture metadata are unknown and never resume. Same-provider turns resume a Codex thread only when it has a non-empty thread id and its authority, effective cwd, and scoped root exactly match the current routing decision. A missing thread id, provider, authority, cwd, or scoped-root change starts a fresh correctly sandboxed thread and bootstraps it from the stored transcript capped at 40,000 characters. This carries visible conversation context across boundaries without treating one provider's private session/tool state or a stale Codex authority as portable. `/fresh` resumes Claude-backed sessions for summarization but summarizes Codex-backed sessions from the stored transcript.

The transport handler derives one provider-neutral authority from scope plus workspace resolution through `resolveChatAccess(scope)`, which selects authority, cwd/root, prompt context, and the composed tool surface together. Home/global is `read-only` with the vault cwd and conversation/KB tools. A product becomes `product-full-access` only when its configured repository exists and its optional scope is relative, exists, and canonicalizes inside the repository. Resolution happens before repo/project context is read; the same canonical workspace/context pair is then reused for prompt assembly, avoiding both pre-validation reads and a second check/use window. Unknown products and stale, malformed, or symlink-escaping repo/scope paths become `product-workspace-write` in a stable per-product SHA-256-derived scratch directory beneath `PRODUCT_CHAT_FALLBACK_ROOT` (default `~/.rune/product-chat-workspaces`) with base read/edit/shell/web tools only. The fallback root is checked before and after creation/realpath resolution to reject overlap with the vault or any configured product repository, and the final product directory may not resolve through an unexpected symlink.

That single routing decision selects the system-prompt capability, tool surface, provider isolation, Codex sandbox, and persisted binding. Fallback prompts describe an unresolved scratch workspace and claim no resolved repository, shared-workspace, full-filesystem, KB, or Cockpit authority. Claude full-access product chats retain repo cwd, the writable-root hint, development tools, and `--dangerously-skip-permissions`; unresolved Claude product chats use the scratch cwd/root, the smaller tool set, the scrubbed product-chat environment, and `--strict-mcp-config` with an empty MCP table. The Claude filesystem boundary remains prompt-level/soft because its permission bypass is deliberate.

Explicit commit completion is a separate fail-closed contract and is considered only after routing resolves `product-full-access`; global and fallback chats never receive repository verification authority. `product-chat-commit.ts` deterministically recognizes direct commit imperatives while excluding negations, questions, and incidental commit terminology. Before provider execution, its bounded Git runner captures the full baseline `HEAD` with a credential-stripped environment. A successful provider return is still reported as confirmed only when post-turn verification finds a different valid `HEAD` that is a verified descendant of the baseline, consistent full/short SHA plus non-empty subject metadata, and an empty `git status --porcelain=v1 --untracked-files=all`. Provider errors, timeouts, cancellations, unavailable/malformed/diverged Git state, unchanged `HEAD`, or any dirty row produce a bounded, secret-redacted and path-scrubbed unconfirmed receipt. Provider prose is retained when present; tool-only completion uses the deterministic receipt as the whole response.

Codex persistence is opt-in at the primitive: chat passes `persistentSession:true`, captures `thread.started`, then calls `codex exec resume` with the stored thread id. The selected authority maps to Codex sandbox mode (`read-only` → `read-only`, `product-workspace-write` → `workspace-write`, `product-full-access` → `danger-full-access`) on every turn. Fresh threads serialize it as `-s <mode>`; resumed threads reassert it as the TOML override `-c sandbox_mode="<mode>"` before any other config overrides and the thread/prompt positional arguments, because `exec resume` does not accept `-s`. Any unknown or differently-bound thread is rotated before dispatch and its replacement receives transcript replay. All pre-existing `runCodex` callers remain `--ephemeral` by default, and the external-sandbox alternative remains mutually exclusive with `sandboxMode`. Both providers register chat operations with the shared in-flight registry, so `/cancel`, cockpit status, shutdown tracking, and path scrubbing retain the same behavior. Every Codex chat retains the secret-scrubbed child environment; product chat never uses the external-sandbox bypass flag.

Fallback Codex is additionally isolated from writable project configuration. It passes `--strict-config`, `--ignore-user-config`, and `--ignore-rules`, replaces the MCP table with `mcp_servers={}`, disables hooks, apps, and remote plugins, disables workspace-write network access, clears configured writable roots, and excludes both `$TMPDIR` and `/tmp` from implicit writable roots. Strict parsing makes renamed/removed security overrides fail closed; the explicit overrides neutralize a hostile `.codex/config.toml`, `hooks.json`, or project `.rules` file without broadening the sandbox. Resolved product Codex instead receives the required isolated seven-tool product MCP configuration; Home/global keeps its read-only posture.

Full-access configured product chats also build a provider-equivalent MCP registration through `product-chat-mcp.ts`. The shared `isolated-mcp-config.ts` encoder produces Claude's complete strict inline registration and Codex's replacement `mcp_servers` table from one server/tool/timeout definition; artifact-role MCP uses the same encoder. User config is ignored, the server is required, and the same seven tools are pinned and approved on both fresh and resumed turns. The child environment is assembled from an explicit safe allowlist plus server-owned `RUNE_PRODUCT_CHAT_PRODUCT`; it does not load `.env.local`, inherit Rune/integration secrets, or receive dummy Telegram credentials. `config.ts` keeps the Telegram fields lazy for this narrow import graph, while `src/index.ts` calls `assertOperatorConfig()` before the full operator process boots. Product-scoped `kb_query` synthesis explicitly invokes `runAgent(..., userVisible=false)`, so it neither reads the operator's Telegram id nor emits operator-only bus/in-flight frames. Home/global never receives Cockpit diagnostics; fallback receives no MCP tools at all.

The transport handler wraps the complete conversation transaction in `withChatTurnLock`: key = transport+user for global chat, product+transport+user for product chat. Session read/create, provider call, transcript append, and executor persistence therefore cannot race for one scoped conversation, while unrelated sessions remain concurrent; a failed turn releases the queue normally. When a provider switch, `/fresh`/`/clear`, or a failed first Codex turn makes a thread unreachable, `cleanupCodexThread` validates the id and best-effort removes only its matching rollout files under `$CODEX_HOME/sessions`.

For a resolved product turn carrying a client-generated `turnId`, the session store records a request hash, commit intent, optional baseline `HEAD`, and `pending` status before invoking the provider. Only a **commit** turn flushes that pending record to disk before execution — it is what stops a restart from re-running a commit whose outcome was never recorded; an ordinary turn keeps in-process identity only and defers its write to completion, holding the hot cockpit path to one synchronous whole-map write per turn. A pending record that cannot be persisted aborts the turn with a bounded reply rather than throwing into the WS dispatch chain, which only logs. Terminal completion atomically persists the assistant transcript entry, stable `messageId`, delivery text, typed commit outcome, verified/observed `HEAD`, and executor binding before sending, and rolls the session back by reference if that write fails. Reusing a terminal `turnId` replays that exact stored message without provider execution; retrying a still-pending turn converts it to a terminal interruption response instead of executing again; a `turnId` returning with request text that does not match its stored hash is refused as a conflict, since neither replaying nor executing under the earlier record is correct. Restore remains compatible with legacy session files lacking `turns`; a persisted pending commit found after restart is terminalized as unconfirmed, and a legacy pending non-commit turn — which can no longer resolve — is dropped.

The Home selector includes GPT-5.6 Terra and synchronizes to the active webview session model; with no session, Terra is selected. Product chat exposes `/gpt-5.6-terra` alongside the Claude quick commands. Existing sessions retain their persisted model rather than being silently moved to the new default.

Within one cockpit page lifetime, `src/server/static/product-chat-session-store.js` owns browser-side product-chat retention independently of the mounted route. `client-view.js` installs one idempotent `rune-webview-frame` consumer; it accepts only explicitly product-scoped chunk/message/status frames and chat operation events, reduces them into exact-slug sessions in arrival order, finalizes one streaming assistant entry with the authoritative message, and closes interrupted streams before a later operation can reuse them. `product-deep-view.js` subscribes to the store for rendering and unsubscribes on close without stopping frame capture. On product load, a successful `/api/state` read reconciles the newest `kind:"chat"` operation whose `scope` exactly matches the product, preserving its original `startedAt` for the elapsed ticker or clearing stale operation/status state when none remains; a failed state read leaves cached state intact.

Product-chat sends generate a `turnId` and carry it through both `POST /api/chat` and WebSocket message frames. Terminal REST responses and WS message frames carry the stored `messageId`; the browser stamps it onto the transcript entry so the retained chat log is the single "already seen" record for both the REST and WS paths, and acknowledges accepted terminal frames. Once the product-chat frame consumer is installed it emits `replay-ready`; the server then replays only unacknowledged commit terminal messages with their original product/turn/message identities, and `message-ack` durably stamps delivery acknowledgment. This adds reload/reconnect durability for commit receipts while ordinary page-lifetime retention remains in the client store; clients that omit IDs retain legacy behavior without exactly-once retry guarantees.

**Live Codex authority acceptance:** `RUNE_ACCEPTANCE_LIVE_CODEX_PRODUCT_CHAT=1 npm run acceptance:product-chat-codex` (`scripts/run-product-chat-codex-acceptance.ts`) uses temporary repositories/directories and the installed authenticated Codex CLI, but enters through the real `handleWebviewMessage` surface. Disposable env/config drives product resolution, prompt/tool/MCP policy, session persistence, and executor reuse. It proves resolved initial/resumed turns can create, modify, stage, and commit; global read-only cannot write in its vault cwd; and a stale configured repo falls back to a dedicated scratch directory that remains writable on initial/resumed turns without allowing sibling/vault writes. Before the fallback turn, the harness plants hostile project Codex config/rules that request an escape MCP server, session hook, network access, and extra writable roots, then proves none fires. Cleanup covers captured sessions and all temporary fixtures even when imports or provider probing fail; the opt-in guard prevents routine test runs from making live model calls.

## In-flight op tracking

Model children register an `InFlightOp` (`src/transport/in-flight.ts`) and emit `BusOpEvent` frames (start/progress/end). TG shows a tracker message ("🤔 agent · 12s · /cancel") that edits every ~10s and deletes on end; the webview shows a cancellable pill. Classifier ops are filtered from senders to avoid resolver spam. Correlated review waves may cancel only named agent roles through `cancelCorrelatedAgentOps`/`forceCancelCorrelatedAgentOps`; these partial operations deliberately do not install a batch tombstone, so satisfying quorum cannot cancel a required designer sharing the batch.

Cancellation uses the provider-neutral `OperationCancellation {operationId, source, requestedAt}` record; source is exactly `telegram`, `cockpit`, or `internal`. `/cancel [opId-prefix]` and `POST /api/ops/:id/cancel` stamp their explicit transport source, and internal callers must pass `internal` explicitly. `cancelOp` is synchronous: the first accepted request is stored before SIGTERM, later requests cannot overwrite its source or timestamp, and the record stays on the live op until the executor captures it immediately before unregistering. Claude and Codex capture on both child `close` and `error`, so an error-event race cannot erase attribution. Their adapters classify SIGTERM/143 as timeout only when Rune's own timeout timer fired; otherwise structured cancellation wins, or the adapter returns `executor-exit` with a bounded CLI terminal reason and duration.

## Mutation pipeline

`src/transport/mutations.ts` is the central registry for autonomous codebase operations (`MutationDescriptor`, applier registry, `createMutation`/`cancelMutation`). The appliers, all registered in `src/index.ts`:

1. **`workRunApplier`** (`src/jobs/work-runner.ts`) — spawns Claude CLI with `spec.md + tasks.md + /work --auto` for a project slug.
2. **`genEvalLoopApplier`** (`src/jobs/gen-eval-loop-runner.ts`, `autoApprove: false`) — validates the `gen-eval-loop` payload and drives `runGenEvalLoop()` (per-round: createWorktree → /work --auto → /review → recordRound → evaluateLoop → destroyWorktree).
3. **`orchestratedWorkApplier`** (`src/jobs/orchestrated-work-runner.ts`, `autoApprove: true`, kind `orchestrated-work`) — creates a sandboxed worktree, drives `runProjectOrchestration` over real fs/git effects with `createProductionTaskWorkflowRunner` as the live per-task role-spawn binding (Phase 8), maps the terminal `OrchestrationResult` to a single `MutationEvent` (finalized→completed, held→completed-flagged-held, blocked→failed).
4. **`workRunReleaseApplier`** (`src/jobs/work-run-release.ts`, `autoApprove: true`, kind `work-run-release`, `supervised: false`) — drives a cold finalize-or-discard of a sentinel/manual-check parked run.
5. **`workRunAnswerApplier`** (`src/jobs/work-run-answer.ts`, `autoApprove: true`, kind `work-run-answer`, `supervised: false`) — answers a parked `AskUserQuestion` and resumes the original parked worktree.
6. **`writingRunApplier`** (`src/jobs/writing-run-runner.ts`, `autoApprove: true`, kind `writing`) — /blog and /writing-critique: drives the writing pipeline (research via in-process MCP tool handlers → writer-SOUL one-shot model stages → privacy-sanitized artifact → commit) against the `writing` product's repo on a create-or-resume `rune-writing/{slug}` branch; V1 publish is branch-commit only (no deploy). Pipeline states surface as run-feed log lines (`publishDerivedRunEvent` gate includes `writing`); a 30s keep-alive ticker shields the silent one-shot model calls from the kind-agnostic quiet→cancel backstop; the worktree is destroyed at terminal on success AND failure (committed work lives on the branch; a kept dirty tree would wedge the slug); one run per slug at a time.

The cockpit Start action dispatches to either the orchestrated or legacy applier via the `src/jobs/work-dispatch.ts` seam — `resolveWorkDispatch` maps the `resolveDispatchMode` decision to a concrete mutation kind; `handleApiMutationsCreate` substitutes `kind:'orchestrated-work'` when orchestrated mode is selected, stamps `dispatchMode`+`fallbackReason` onto the payload, and always records which applier ran. Both `orchestrated-work` and `work-run` share the same deterministic per-project worktree path and the same per-project + global concurrency caps, so the two never run the same project concurrently.

Mutations are logged append-only to `logs/mutations.jsonl`; orphaned `running` entries are flipped to `failed` at startup via `reconcileOrphans()`.

**Shutdown-park suppression:** `setMutationShutdownInProgress(v)`/`isMutationShutdownInProgress()` is armed by `shutdown()` (`src/index.ts`) before `killActiveProcesses()`. While armed, `startApply` suppresses ALL terminal/crash persistence and heartbeat upserts, but ONLY for `orchestrated-work` mutations — a SIGTERM'd child would otherwise surface as a terminal the run never earned, flipping a boot-resumable `running` mutation to `failed` or clobbering a just-written shutdown park. Other mutation kinds keep their existing crash semantics. A suppressed run's `activeRuns` handle is also retained (not deleted in the `startApply` finally) so the parker — which snapshots `activeRuns` only after the children are dead — can still find the run after its applier unwinds. See the shutdown-park entry below for what owns the suppressed run's on-disk state instead.

### Supervision coupling

Every mutation state transition drives `src/jobs/supervision-store.ts`: `createMutation` seeds a `SupervisedRun` (`running` for autoApprove, `blocked-on-human` for pending-approval); `startApply` flips to `running`; `output` events refresh `lastHeartbeatAt` and advance `lastOutputAt` (both throttled to once per 30s — `lastOutputAt` is the LLM-output signal the quiet-run nudge keys on, distinct from `lastChildAliveAt`); verified activity uses `recordRunActivity`, whose atomic read-modify-write deliberately clears `quietNudgedAt` so a later quiet period can form a fresh cycle; non-output writes thread the current `lastOutputAt` through so it is never reset to undefined; `completed`/`failed` and applier-crash paths flip terminal status. A superseded max-runtime request also stamps optional `maxRuntimeEpochAt`; legacy rows omit it and continue measuring from `startedAt`. `runTargetFromDescriptor` resolves and persists the same `{kind:'project'|'bug',slug}` target on supervision rows and run-feed events, with legacy payload fallbacks. Routine supervision writes are fail-safe; cancellation supersession fails closed if its required activity-reset write cannot persist. The audit source of truth remains `mutations.jsonl`.

## Supervision & stall-check

`SupervisedRun[]` current state persists to `logs/supervised-runs.json` (`supervision-store.ts`). `upsertRun` **field-merges** by id so a keep-alive heartbeat can't accidentally clear `quietNudgedAt`; `recordRunActivity` is the explicit clearing operation when actual output proves the quiet period ended. The store then applies a 768 KiB visibility budget by preserving every running/parked row and retaining only the newest terminal rows that fit. Terminal history remains durable in per-run summaries and `mutations.jsonl`; this keeps the diagnostics complete-reader below its 1 MiB fail-closed ceiling during normal operation. If active rows alone exceed the cap, they are never dropped and diagnostics correctly remain unavailable until state contracts. The stall-check runner (`stall-check-runner.ts`, 30s tick) runs on a single snapshot:
- `checkStalledRuns` → newly-nudged-id set (child-dead stall, 5min threshold).
- `planQuietNudges` over the non-stalled remainder (quiet-but-alive, keyed on `lastOutputAt`, 5min threshold) → publishes `formatQuietNudge`, persists `quietNudgedAt`.
- **Escalation (project 15 P2.7):** `planQuietCancel` (quiet past `WORK_RUN_QUIET_CANCEL_AFTER_MS` since nudge → `cancelMutation(..., 'system', 'quiet-run')`), `planMaxRuntimeKills` (running past `WORK_RUN_MAX_RUNTIME_MS` since `maxRuntimeEpochAt ?? startedAt`, regardless of liveness → source `max-runtime`, fail-toward-kill on corrupt timestamp).
- `planParkedNudges` over `blocked-on-human` runs (one-time staleness nudge after `PARKED_RUN_NUDGE_AFTER_MS`, never auto-releases).

Per-run send/persist/cancel/kill errors are individually caught so a failure on one run can't skip the rest; tick exceptions caught so a failure can't crash the server.

## Work-run lifecycle

`workRunApplier` spawns Claude CLI with `--output-format stream-json --verbose` and converts each stdout envelope into human-readable `output` `MutationEvent`s via the stream-json→display adapter (`work-run-transcript.ts`). The terminal sequence:

- Tees raw envelopes to a per-run durable transcript sink (`<id>/transcript.jsonl`).
- Classifies on work product via `computeWorkProduct` + `finalizeWorkRun` (`work-run-classify.ts`) — outcome ∈ branch-complete / partial / noop / dirty-uncommitted / failed.
- Flushes transcript (awaits finish), writes `summary.json` atomically with the durable project-or-bug target identity and optional scrubbed nested-role cancellation correlation, appends a `WorkRunIndexRow` to `logs/work-runs/index.jsonl` (best-effort).
- Augments the terminal event with `projectSlug`+`product` so the cockpit and `formatWorkRunTerminal` can name the run.

**Start event (project 13 Phase 1a):** once `createWorktree` succeeds, yields a one-shot `start` `MutationEvent` carrying `operatorWorktreePath` (un-scrubbed) + `runId`/`projectSlug`/`product`. **The path is LOCAL-OPERATOR-ONLY and is never copied onto the descriptor**, so it never reaches `mutations.jsonl`/summary/index/transcript/forensics. The createWorktree-failure branch returns before this point so a run with no worktree emits no `start`.

**Parked state (project 13 Phase 1b + AskUserQuestion loop):** when the stream contains either a valid `RUNE_WORK_RUN_SENTINEL` (parsed via `parseWorkRunSentinel`) or a Claude `AskUserQuestion` assistant `tool_use` (parsed via `work-run-question.ts`), and the run was NOT user-cancelled, work-runner writes a durable `blocked-on-human` supervision record FIRST, SKIPS `runFinalizer` (leaves the worktree live), and yields a terminal event carrying `parked:true` + un-scrubbed `operatorWorktreePath`. Sentinel/manual-check parks carry `pendingCheck`/`command`/`reason` and render a one-tap "Release" action (`work-run-release:<id>`) that cold-finalizes or discards. Question parks additionally persist `SupervisedRun.parkedQuestion` (`source:'ask-user-question'`, question, stable option ids, labels/values/descriptions, `toolUseId`, `askedAt`) and render one answer action per option (`work-run-answer:<runId>:<optionId>`). A malformed `AskUserQuestion` still parks with an inspect-transcript fallback, never silently classifies as `noop`/`partial`.

**Answer resume:** `requestWorkRunAnswer(runId, optionId)` validates the parked run, structured question, option id, and live worktree, then creates the auto-approved `work-run-answer` control mutation. The applier flips the original run id back to `running`, spawns Claude in the existing worktree with the selected answer and retained worktree-derived `RUNE_VITEST_CACHE_DIR` injected, appends to the original transcript, and yields terminal bus events keyed to the original run id. A second `AskUserQuestion` parks again with a fresh `parkedQuestion`; otherwise the existing gated finalizer path classifies/lands/holds the resumed worktree. This path is distinct from Release: answering continues work, Release finalizes a non-question park.

**Commit-poll ticker (project 11 Phase 4):** `streamProcess` runs a parent-side commit-poll ticker (10s, unref'd, re-entrancy-guarded) — each tick calls `git log baseSha..branch`, reads `tasks.md` tally via `parseTasks`, passes both to `planCommitProgress`, and enqueues a scrubbed throttled `progress` `MutationEvent` when a new commit lands. Enabled only when `sandbox.baseSha` is present.

**Forensics (project 11 Phase 3):** `exportForensics` writes a reconstructable evidence bundle to `logs/work-runs/<id>/` BEFORE the worktree is destroyed; best-effort by contract.

**Model-facing diagnostics:** `work-run-diagnostics.ts` projects summaries, supervision, recent task records, and display transcript tails for the dedicated product-chat MCP surface. Authorization is server-owned and fail-closed across every persisted ownership record before task/transcript readers run; unknown and foreign runs share one unavailable response. Summary reads are tri-state: a genuinely missing summary may fall back to complete supervision evidence, while invalid, malformed, or unreadable summary evidence denies access. `readAllRunsBounded` reads the supervision snapshot only when the complete file fits its byte cap and returns `complete:false` for oversized, unreadable, malformed, or partly invalid state; diagnostics refuse authorization whenever completeness is false, so omitted older ownership evidence cannot widen access. DTOs expose the persisted project-or-bug target identity (legacy records fall back to project), the durable `{role,operationId,source,requestedAt}` cancellation record after the live child is gone, task-scoped coder-self-review/artifact-attempt or typed execution-failure evidence, and only runtime-validated compact task/merge validation receipts when present. Execution failures and validation receipts pass explicit field allowlists before projection, so corrupt or excess persisted fields cannot cross the model-facing boundary. Index/task JSONL and transcript display readers share the fixed-byte text-tail primitive in `jsonl-tail.ts`, which reports source truncation and drops a partial leading line. Readers also bound record counts, transcript bytes (512 KiB), strings, nested object entries, and final JSON (64,000 characters), while recursively redacting secrets and scrubbing host paths—including cancellation and artifact-diagnostic fields. They never return raw JSONL, terminal artifacts, full validation attestations, artifact/worktree paths, cookies, or mutation controls.

**Isolated Vitest caches:** every active worktree maps to an opaque deterministic cache at `<os-temp>/rune-vitest-cache/<sha256(absolute-worktree-path)>`. Rune forces that path through `RUNE_VITEST_CACHE_DIR` for sandboxed agents, both initial and answer-resumed legacy work-run Claude children, and closeout/gate validation commands; inherited or product-credential values cannot override it. `vitest.config.cjs` consumes the variable and, by being CommonJS, avoids Vite's separate ESM config-bundle write to shared `node_modules/.vite-temp`. A parked worktree keeps its cache for resume. Normal/idempotent destruction, preserved-worktree reclaim, reconciliation rollback, integration-gate teardown, and orphan cleanup remove the matching cache best-effort; cleanup failures never mask the worktree result.

**Canonical full-suite validation:** every exact `validationCommands` entry has one `validationCommandProfiles` assignment: `isolated`, `loopback`, or `sandbox-integration`. Live config parsing rejects missing, duplicate, unknown-command, and unknown-profile assignments. `validationAdapters` remains an exact typed runner mapping and may add `profileSelection:"strict-tags-v1"`; Rune/Rune-MCP use it for `npm test`. The planner expands strict Vitest commands in stable isolated → loopback → sandbox-integration order using the `validation-loopback` and `validation-sandbox-integration` tags, with untagged tests isolated and conflicting capability tags invalid. Conflicting tags are enforced where per-test resolved tags are visible — Rune's trusted Vitest reporter counts each conflicting test as a collection error, so the lifecycle fails to reconcile and the shard fails closed rather than skipping the test in every shard under green counts. The plan, selectors, and definition fingerprint are fixed before execution and shared by admission, confirm-red, closeout, related selection, and the merge gate.

Provider-neutral V1/V2/V3 durable schemas and strict historical readers live in `intent/full-suite-attestation.ts`; the trusted host capability, fingerprint, authenticated-reader, and gate-receipt boundary lives in `jobs/full-suite-attestation.ts`. Module initialization resolves the trust root from the installed Rune module URL—not `PROJECT_ROOT`, workspace/product config, or test-mocked filesystem state—and uses native filesystem calls to hash reporter/observer/extractor source plus the complete installed Vitest, `@vitest`, and Vite runtime (bounded file/count/byte walk with symlinks rejected). Every later adapter capture must match that boot anchor. `runFullSuiteValidation` captures the staged canonical Git tree and full-task review hash plus complete normalized shard argv, validated relative cwd, profile plan/outcomes, and command/adapter/configuration/dependency/implementation/trusted-runtime fingerprints before and after execution. V3 additionally hashes the stripped validation environment and resolved executable toolchain and derives a canonical receipt ID from the full reusable identity. V1/V2 evidence remains parseable but cannot authorize the V3 post-review handoff.

Before dispatching a selected profile, Rune runs a fixed capability probe under the same definition: isolated proves network denial, loopback proves local bind/connect plus external denial, and sandbox-integration proves broker operation. The sandbox-integration test child may contact only a private Unix socket. The Rune-owned broker accepts bounded candidate profiles and a predefined scenario only, rejects arbitrary commands/cwds/environments/host-path grants, and starts fixed boot-owned probes as top-level `/usr/bin/sandbox-exec` children with empty environments and private temporary roots. Startup, socket containment, validation, cancellation, process cleanup, and teardown fail closed. Probe failure becomes typed `profile-unavailable`; admission blocks before roles, while later discovery becomes a WIP-preserving operational hold rather than coder feedback.

For each eligible full Vitest shard, Rune first materializes `expectedTreeOid` into a fresh temporary checkout through an isolated Git index, then links only Rune's boot-anchored `node_modules`. It rechecks both lexical and real materialization/cwd containment. The observer is assembled from captured source and launched as `node --input-type=module -`; source, output path, extractor/reporter source, selected tag filter, and fresh one-run capability travel only through anonymous stdin. The capability-free extractor receives only toolchain `PATH` and the isolated cache, evaluates at most one bounded local config, and emits bounded JSON. The observer accepts only allowlisted declarative settings and exact validation tags, disables ordinary product config loading, forces fork workers, and installs the trusted counts-only reporter. Observer and exact shard receive the same network profile; both deny writes to Rune's trust root, the observer additionally denies its reviewed materialization, and the exact command re-allows only the concrete validation worktree's lexical/real roots.

Only after the observer attempt is quiescent does Rune execute the exact configured shard independently in the real validation cwd with no attestation material; setup/confinement/observer failure never suppresses it. Reporter callbacks record only aggregate discovered/completed suite/test buckets and HMAC-authenticate the bounded envelope. Every child carries a private process nonce; leader exit triggers process-group quiescence plus bounded macOS scan/kill/rescan of detached descendants before evidence or Git recapture. Once all expected shards are green, one V3 aggregate attestation covers the complete plan; mapped Vitest lifecycles also reconcile and sum their totals. Green pre-closeout reuse requires unchanged complete identity, exact cwd/argv, green per-profile outcomes, and confirmed cleanup; `vitest-related` additionally requires authenticated complete lifecycle evidence, while `product-commands` may accept unsupported lifecycle coverage after every configured shard passed. Profile unavailability, missing/malformed/unauthenticated/partial evidence, identity drift, timeout, cancellation, assertion failure, and uncertain cleanup remain distinct non-reusable outcomes.

Outer-confinement ownership is explicit: trusted validation and artifact launchers mint nominal in-memory capabilities bound to the exact owner and profile path. Codex's external-sandbox bypass requires that capability; a spoofed object, plain environment marker, missing capability, ambiguous owner, or request for an inner sandbox under an outer owner is rejected before spawn. The private compatible-mode environment marker survives only for the legacy/unprofiled related-test transition and is not confinement proof.

**Retention GC:** `gcWorkRuns` prunes `logs/work-runs/` artifacts oldest-first to satisfy `WORK_RUN_RETENTION_MAX_RUNS` + `WORK_RUN_RETENTION_MAX_BYTES`; protected set = activeRuns + non-terminal run-store + worktree-checked-out branches. Runs at startup and on each run completion (fire-and-forget).

## Gated-merge finalizer (project 15)

`runFinalizer(input, effects)` (`work-run-finalizer.ts`) is the shared idempotent phase-recorded finalizer, records a durable phase per step (`logs/work-runs/<id>/phase`) for crash-resume.

- **`hold` mode** (P0.4a): classify → flush transcript → write summary/index → resolve worktree (best-effort removal, branch left intact) → terminal supervision write. NEVER merges/pushes/deletes; never leaves the run `running`.
- **`gated-merge` mode** (P1.5 + Phase 3.5, live via `runGatedMerge`): classify → flush → summary → index → gate → green-receipt write → cancellation recheck → merge → push → delete → terminal, recording `merged-not-pushed` then `pushed-not-deleted` (**push-before-delete: origin is the durable backup**); consults `readLastPhase()` for crash-resume (skips an already-committed merge/push/index-append — exactly-once); a failed/cancelled gate STOPS at branch-complete and alerts (never merges); a non-branch-complete run never consults the gate.

The pure gate DECISION (`evaluateGate`), gate RUNTIME (`runGate` — runs the same attested launcher in an integration worktree so a red check never mutates `main`), and per-product/per-base-branch merge lock (`withBaseBranchLock`) are all wired as effects from `work-runner.ts`. The gate always probes and executes every selected profile shard independently of task-closeout reuse; a supported command contributes lifecycle coverage while an unsupported command remains execution-required. Before `mergeBranch`, the finalizer requires a green schema-valid V3 gate receipt carrying canonical integration tree/review identity, completion time, exact profile plan/definition fingerprint, per-profile probe/outcomes, command/configuration/dependency/environment/toolchain fingerprints, and semantically consistent shard coverage counts. It atomically persists that receipt mode 0600 as `<run>/gate-validation.json`, then rechecks cancellation inside the base-branch critical section. Assertion failure, profile unavailability, invalid evidence, receipt-write failure, or cancellation prevents merge. The identity-bearing receipt is copied to terminal facts/summary and restored by release/recovery readers; Cockpit and Telegram show selected profiles and label capability unavailability as an operational hold. Recovery after a recorded merge reuses its durable authorization while recovery before merge reruns validation. V1/V2 records remain readable but cannot authorize V3 execution. `resolveWorktreeAndFinalize` runs `onBranchDelete` AFTER `removeWorktree` and BEFORE `git branch -d` (git refuses to delete a checked-out branch).

Live consumers: the live work-runner `apply()` terminal path (gated-merge mode) and the startup recovery path (`recovery-finalize-runner.ts` — hold mode by default, gated-merge to RESUME a crashed-mid-merge run off its durable phase, never to initiate one).

## Orchestrated work & product-team agents (project 14)

The orchestrated path is OFF by default (`ORCHESTRATED_WORK_ENABLED=false`); a per-product `orchestratedMode: true/false` in `policies/products.json` overrides it. When on, the cockpit Start action routes to `orchestratedWorkApplier`.

**The eight product-team roles** (`src/roles/loader.ts`): `pm`, `tech-lead`, `qa`, `coder`, `reviewer`, `designer`, `security`, `adjudicator`. Each has a SOUL charter and a `memory.md` under `agents/<role>/` (mirroring `agents/writer/`). Two-channel authority boundary: SOUL.md → system-prompt, memory.md + exemplars → low-authority reference fences. Judgment roles run on policy-selected bindings; artifact roles run through Codex in the current policy. Reviewer/coder provider distinctness is enforced at resolution time, but an unavailable independent reviewer is now one failed eligible path rather than an early task block—the tech-lead and selected security remain able to satisfy quorum, and reviewer fallback never reuses the coder. Optional `roleEscalations` entries for reviewer/tech-lead/security select the second and final operational retry; invalid/deprecated entries fall back to the base binding, and a reviewer escalation must remain provider-distinct from the coder. There is exactly ONE `adjudicator` binding (→ gpt-5.6-terra). It is a DECLARED policy choice rather than a runtime distinctness computation: reviewer and tech lead are both anthropic, so it sits on the openai side by design and receives fresh context. It must be distinct from both disputants **and from the coder** — the adjudicator rules on the coder's own artifact, so binding it to the coder's model would let the author cast the deciding vote on whether that artifact is defective. An unavailable declaration blocks production before preflight and never falls through to a global default. **A task adjudicates at most once**: every adjudication branch returns a terminal outcome. The two ways in — a dispute signature that survived a coder retry, or the round cap — are both last-call moments on a split that would otherwise end the task, so they share one model rather than two bindings. The `escalate` flag survives as evidence and as prompt context (it tells the adjudicator a coder round already failed to settle this objection) and as the record's `escalated` field, but it selects no model. Aliases are policy data — `policies/model-policy.json` is the source of truth, not this list.

**Security-sized pre-coder invariant review:** after executor preflight and reviewer-independence, but before QA, `securityNeeded` tasks run sequential read-only inspections: tech lead drafts repository-backed invariants and security ratifies every draft ID into one authoritative checklist. `src/intent/invariant-review.ts` owns the strict fence/JSON schema, five fixed categories, item/text/reference bounds, real-file containment and anchor checks, contradiction handling, secret/path sanitization, canonical rendering, and content hash. Production calls use the worktree cwd, product-scrubbed environment, strict empty MCP, no network-capable tools, and only `Read`/`Glob`/`Grep`; unsupported executor formats fail closed. That read-only narrowing is the `--tools` flag, not an OS sandbox — `execClaude` always prepends `--dangerously-skip-permissions`, so containment here is a deliberately accepted defense-in-depth posture, not an enforced boundary (CLAUDE.md → Invariants → *Pre-coder invariant review is flag-contained, not OS-contained*). The exact canonical bytes are advisory and non-exhaustive in QA, test-intent, coder/self-review, and every ordinary post-coder judgment prompt. Because those bytes reach roles that do hold Bash/Edit/Write, and because each item is model-authored text quoted from repository files, the block leads with an explicit untrusted-content framing — reference material, never instructions — positioned ahead of every item. They never replace reviewer independence, post-coder reviewer/tech-lead/security, validation, closeout, or merge gates. Accepted checklist evidence and typed operational failure metadata round-trip through task records and diagnostics; Cockpit activity receives only a bounded stage/hash/count event, never raw role output. Unflagged tasks retain the prior QA-first fast path.

**The post-implementation gate has three stages, in order.** Each closes a hole that let one weak objection stop a run (see the four closed entries in `docs/projects/bugs.md`):

1. **Evidence contract** (`src/intent/finding-evidence.ts`, applied in the workflow between verdict normalization and the ledger merge). A blocking finding in a `concurrency`, `data-integrity`, or `security` class must carry a concrete location and a failure scenario. What does not gets ONE bounded re-prompt on the role's own model (`requestFindingEvidence`); what still does not is downgraded to a non-blocking observation, recorded on `TaskEvidence.downgradedFindings`, and filed as a follow-up. A finding citing a reproducible failure is exempt outright. Scope is deliberately narrow: findings only (a bare fail with no findings is ordinary quality disagreement) and blocking severities only (`low` maps to pass-with-warnings).
2. **Split adjudication** (`adjudicateSplit`). Only a reviewer-vs-tech-lead disagreement is a tie. Designer remains a separate required gate when flagged; security is quorum-eligible when flagged, but a security objection is not a reviewer-vs-tech-lead split and still enters the ordinary objection path. An eligible split dispatches one adjudicator with fresh context and both verdict texts only when it would otherwise END the task: the same objection survived a coder retry, or the round cap is next. High/critical and explicitly irreversible objections anywhere in the open ledger are mechanically withheld for a human and cannot be cleared by an adjudicator response. A ruling for the pass resolves and files only the current dissent's findings, and closes the task only when no other blocking finding remains; a ruling for the fail records a concrete finding, blocks, and marks the terminal `adjudicationUpheldFail` so surfaces read the substantive/operational split off typed state rather than the reason prose (the marker and `adjudicationFailure` are mutually exclusive; summaries claiming both fail closed, and pre-marker runs fall back to the reason text). The strict parser admits only `pass`, or `fail` with a nonblank rationale and an evidence-complete finding. Missing/invalid fences or JSON, unsupported verdicts, blank rationale, missing/malformed findings, and evidence gaps are bounded diagnostic codes, never synthetic fails. The production seam builds the split body once and permits exactly one schema-correction retry on the same model with byte-identical diff/spec/tests/verdict evidence. A second invalid artifact, provider/executor failure, or unavailable production binding yields typed `adjudication-output-invalid` operational evidence, preserves the branch/worktree, emits no substantive role verdict, adds no finding, and generates no coder feedback. Records are discriminated as `ruling` versus `operational-failure`; status-less historical records normalize as rulings. Only scrubbed attempt codes and trusted executed alias/provider survive into task records, terminal data, summaries, and Cockpit—raw replies remain transient. The optional pure/legacy workflow seam may still be absent and retain its pre-adjudicator terminal behavior; production never uses that compatibility path.
3. **PM acceptance at the cap** (`acceptWithRationale`, per `agents/pm/SOUL.md`'s "wrap up at the cap"). Only a block surviving every coder round reaches it, and in practice only findings-FREE disagreement does: any open finding is at least `medium` and `PM_ACCEPTANCE_MAX_SEVERITY` refuses medium-and-above, as does any irreversible finding. The PM receives the actual dissenting role/verdict, spec, canonical full-task review artifact, tests, and complete findings ledger—not a reviewer-shaped proxy. Acceptance requires a non-empty rationale; the actor, rationale, dissenting role, and overridden verdict are recorded durably, and a secret- and host-path-scrubbed `pm-acceptance` operator notification is emitted. A missing seam, a throw, a refusal, or an empty rationale leaves the block intact.

**QA holds no post-implementation gate.** QA authors tests from the spec, the tech lead reviews that intent, and QA's work on the task ends when the coder starts. Its former `diff-revalidation` stage read the same artifact the reviewer and tech lead read, returned a bare boolean, and ran on the coder's own provider family — the one gate that violated the distinct-provider review rule. QA is absent from both the live post-coder batch and its durable checkpoint. The test-integrity questions it nominally owned (was a test deleted, weakened, or retargeted; is behavior untested; does the code satisfy a test's shape without its intent) are part of the tech lead's diff-review prompt.

**Durable post-coder quorum:** `coordinateReviewBatch` fans reviewer, tech-lead, optional designer, and optional security over one frozen canonical `JudgmentContext`. Reviewer, tech-lead, and selected security are quorum-eligible: the first pass/pass-with-warnings can satisfy eligible quorum. The conditional designer is marked `required`, not quorum-eligible, and must separately pass. Any completed fail from any participating role is an objection. Before a pass may cancel siblings, the coordinator drains every already-settled model result through bounded evidence-contract finalization; a completed objection therefore wins over a contemporaneous pass. Satisfying eligible quorum cancels only unresolved eligible siblings and allows a live designer to finish. Objection/external cancellation stops only unresolved members. Named-role cancellation avoids the batch tombstone used by whole-wave cleanup; SIGTERM-ignoring children receive bounded role-targeted SIGKILL cleanup.

`src/intent/review-batch-state.ts` owns the version-1 durable schema and parser. The cursor snapshot binds batch/task/round/workflow attempt to the stable task-base tree, exact current tree, canonical diff hash, exact role set, per-attempt model/provider/format/status/timing, bounded normalized verdict or operational diagnostic, cancellation reason, and bounded resume context. The resume context includes accumulated and coder handoff notes, test-intent repair evidence, and prior adjudication audit records with executed model/provider attribution, alongside the other convergence state needed to continue the round faithfully. It is checkpointed before the wave and after every transition. On restart Rune re-captures Git identity before invoking a role, rejects task/tree/hash or role-set drift as a typed operational hold, reuses completed normalized verdicts, and converts an in-flight attempt to `interrupted` while preserving the two-attempt budget. Each eligible role may retry an operational failure once. Attempt two uses an explicit valid declared escalation; if none exists, it freezes and reuses the preceding attempt's durable model/provider/format despite policy reload or restart, and that exact binding reaches the provider spawn. Designer is not retried. Exhausted eligible paths, required-designer unavailability, review-surface drift, and checkpoint failure are distinct `ReviewQuorumFailure` categories, never synthetic negative verdicts.

**Executor readiness preflight:** before the first automated task invokes any product-team role, `createProductionTaskWorkflowRunner` resolves the run's model policy and calls `execution-preflight.ts` before building production workflow dependencies. Ordinary failures after a successful preflight retain the existing role-failure path and are not labeled as preflight failures.

**Typed execution failure + bounded retry:** the shared intent-layer contract in `src/intent/execution-failure.ts` replaces durable executor error strings with `ExecutionFailure`: task, role, provider, CLI format, exact model, workflow stage, failure stage (`artifact-mcp`, `artifact-contract`, `environment`, `spawn`, `timeout`, `cancellation`, `provider`, `executor-exit`, `git-stage`, `git-diff`, or `orchestration-adjacent`), bounded scrubbed diagnostic, retryability, failed-attempt history, retry disposition, and optional cancellation correlation. `ArtifactAttemptEvidence` records only attempt number, provider, terminal-artifact state (`captured`, `parsed`, `missing`, `malformed`, `ambiguous`, `non-final`, or `rejected`), bounded progress/candidate counts, and a scrubbed diagnostic; checkpoints, execution attempts, failures, and successful self-review records may carry at most two such rows while historical records may omit them. `runExecutionAgent` permits two total fresh-process attempts. Spawn failures, timeouts, documented retryable provider events, and generic nonzero executor exits are eligible for one retry after a jittered 1–2 second backoff. Exit 143 or `SIGTERM` alone is not timeout proof—the adapter's own elapsed timer must have fired. This snapshot covers tracked and non-ignored untracked repository content—ignored files, `.git` metadata, and non-filesystem/external side effects are excluded by design. **Flow:** `runProjectOrchestration` (`project-orchestrator.ts`) drives tasks to completion: while an unchecked task remains: `selectNextTask` (including adjacent `validationPolicy`, legacy default `required`) → `assembleTaskContext` → validation admission before role policy/preflight → `runTaskWorkflow` (the workflow owns per-task convergence internally) → cancellation boundary → on `ready-for-closeout`, Rune-owned `runPreCloseoutValidation(task, evidence)` executes the complete configured profile plan once → `runCloseoutChecks(task, evidence, candidate)` explicitly receives and revalidates that candidate → only after both pass, mutation-only `performCloseout` (curate+`applyContextUpdate` → `markSelectedTaskComplete` → commitCloseout → verifyCleanWorktree). Rejected role rounds never invoke the stage. A closeout-repair workflow or recovered in-progress task obtains fresh evidence rather than carrying a prior candidate across the boundary. Before dispatch, provisioning realpath-checks the resolved project directory and managed `spec.md`/`tasks.md`/existing `context.md`; symlinks and worktree escapes fail closed. Authoritative managed-file reads repeat real-parent/file containment and open with `O_NOFOLLOW`, rather than trusting the earlier snapshot. Required-task admission proves a non-empty parseable command list, a real worktree-contained `validationCwd`, and every command executable before QA/coder dispatch; only explicit `reviewed-no-validation` bypasses admission and closeout commands. Typed `executionFailure` evidence routes directly to an operational hold independent of its diagnostic wording; validation/policy/preflight blocks, findings, ordinary gate rejections, and cancellation retain their distinct routes. Cancellation state carries source through `ApplyContext` → runner → `OrchestrationDeps` and into the Rune-owned validation launcher; cancellation stops later configured commands, reaps the current process group, and cannot produce green evidence. User, shutdown, recovery, and unspecified system requests stop before closeout. Quiet/max-runtime requests also stop blocked/failed/cancelled evidence, but `ready-for-closeout` is strong enough to atomically clear the still-active watchdog request; the orchestrator emits one scrubbed `system-cancel-superseded` output (durable transcript + live run feed), then closes out and selects the next task.

`runPreCloseoutValidation` re-admits the required task and runs the complete configured command list through the Rune-owned attested launcher under `WORK_RUN_CLOSEOUT_COMMAND_TIMEOUT_MS`. A green run creates a V3 candidate whose canonical receipt ID binds the reviewed tree/hash, relative cwd, normalized shard argv, profile plan/definition, command/configuration/dependency fingerprints, hashed stripped validation environment, resolved toolchain, timing, execution outcome, and any trusted lifecycle coverage. `runCloseoutChecks` stages and recaptures the canonical review surface, then calls `captureFullSuiteValidationIdentity` without launching product code. Only an exact field-by-field V3 identity can record `full-suite-reused`: `product-commands` accepts an all-green configured batch even when lifecycle coverage is unsupported, while `vitest-related` additionally requires complete green trusted Vitest coverage and therefore skips its related spawn only in that case. V1/V2 remain parseable history but never authorize this handoff. Missing/corrupt/incomplete/cancelled evidence, canonical recapture failure, and tree/review/argv/cwd/profile/configuration/dependency/environment/toolchain drift record one bounded invalidation reason and take the existing related/full closeout fallback. Red or timed-out stage execution enters the ordinary bounded repair/hold path before closeout. The fallback rebases normalized, deduplicated tracked/untracked paths from the worktree root to validated `validationCwd` before argv-spawning Vitest (deleted paths and global configuration changes run the complete command list); selections beyond the durable path/count/total-size contract also use full product validation.

The extracted `runRelatedTestCloseout` state machine classifies a failed related run from the private Vitest JSON report only. That untrusted path is opened nonblocking/no-follow and must resolve through the anchored descriptor to a regular file; Rune reads at most 2,000,001 bytes, rejects reports over 2,000,000 bytes, retains 25 errors, bounds file/test names to 1,000 characters and messages to 2,000, and scrubs each complete field before truncation. The parser returns an exact error total and completeness bit. Every complete structured error must match supported nested-Seatbelt `sandbox_apply` denial or loopback `listen` `EPERM`/`EACCES` evidence before the run is a validation-host conflict. Missing, malformed (including nested shapes), special-file/symlinked, oversized, truncated/incomplete, timed-out, or mixed assertion/infrastructure evidence remains `related-test-failure`; its bounded structured assertion/suite details join the normal qa→coder repair feedback instead of being inferred from console output.

The `RelatedTestDiagnostic` discriminated union/runtime guard enforces state invariants: the initial invocation is failed and non-compatible; ordinary/conflict states have no fallback; a conflict has complete, non-empty, fully classified evidence; fallback states carry the identical validated cwd, command, argv, and selected paths in compatible mode; and pass/fail state agrees with a complete zero-error exit-0 result. A confirmed conflict reruns that exact selection under the normal outer Seatbelt and secret-free environment. The reserved marker only tells Rune-owned validation/Git helpers to omit an unsupported nested Seatbelt; marker presence is not confinement proof, and safety relies on the production launcher's provenance (`assertOperatorConfig()` rejects the marker in an operator environment). `related-fallback-failed` (timeout/unsupported/unsafe included) or a standalone confirmed conflict routes immediately to a WIP-preserving operational hold without consuming coder/QA repair rounds or writing context/task closeout state.

Each scrubbed initial/fallback diagnostic appends to `<run>/related-test-diagnostics.jsonl` with `recordedAt` and `taskId`. Successful fallback evidence is stored on its `TaskRunRecord`; finalization collects the newest 20 task-attributed records into `relatedTestDiagnostics` and threads that bounded aggregate through finalized result, terminal data, `WorkRunSummary`, authenticated diagnostics, and Cockpit. `relatedTestDiagnostic` remains the singular latest-record compatibility projection, and readers validate list/latest agreement while accepting historical records that omit either optional field. Transcript/feed activity emits the bounded stage result and closeout decision. Authenticated diagnostics and terminal summaries retain that bounded record, and product deep-view renders duration, reuse/fallback state, invalidation code, and only the first 12 receipt-ID characters; it separately shows the independent merge-gate outcome/command count. No surface receives full attestations, fingerprint inputs, environment values, resolved tool paths, reporter paths, capabilities, raw test names/output, absolute paths, secrets, or unbounded data. After either a reusable/ordinary green run or `related-fallback-passed`, closeout stages and writes the current tree again, derives the full-task artifact against the same durable task base, and requires both its hash and current-tree OID to equal the review-approved identities. The extracted `commitReviewedCloseoutTree` effect materializes the prepared `context.md`/`tasks.md` bodies as temporary mode-0600 files, seeds a private `GIT_INDEX_FILE` from the exact reviewed tree, hashes only those prepared blobs, and rejects any tree delta outside the two managed paths. It then creates the commit directly with `git commit-tree`, compare-and-swap advances the intended branch with `git update-ref`, and refreshes the shared index only after the ref update; current evidence never uses mutable-index `git commit`, so concurrent worktree/index dirt cannot enter the reviewed commit. Real-Git regressions cover shared-index/worktree isolation and compare-and-swap refusal after concurrent branch movement. Validation failures append bounded, scrubbed `task-validation-failures.jsonl`; review-surface mismatches append only tree OIDs, hashes, and changed paths to `review-surface-failures.jsonl`, never raw diff content. A red product check enters the bounded repair loop (`CLOSEOUT_REPAIR_CAP` = 2 whole-workflow re-runs) with the original task base preserved; exhaustion best-effort WIP-commits and parks `blocked-on-human` with no context write, task tick, or closeout commit.

`context-curator.ts` is the only writer of Rune-owned `context.md`. Before applying bodies it deterministically migrates the exact legacy `## Canonical Interfaces` heading in place, preserving its body, and upserts missing canonical sections with `_None yet._`; afterward all five canonical headings must occur exactly once. Duplicate canonical or legacy headings, a legacy/canonical collision, and managed headings embedded in update bodies are refused rather than merged heuristically. The refusal names the canonical heading, retains an exact conflict count with at most ten displayed headings when relevant, and provides a bounded repair. Because context and task transforms are computed before either write, this path writes neither file and creates no closeout commit. At the effect boundary, provisioning and closeout share `managed-worktree-fs.ts`: it validates both managed paths, opens with `O_NOFOLLOW`, verifies the descriptor against the current contained pathname, rejects hard links, and truncates only after verification. Node lacks `openat(2)`, so the explicitly documented residual hostile ancestor-rename race is outside the serialized, post-child-reap closeout threat model. The orchestrator attempts a discriminated WIP checkpoint (`committed` with SHA, `already-clean`, or `failed` with a scrubbed diagnostic) and returns a failed operational hold with the worktree preserved—not `blocked-on-human`. The runner derives the scrubbed relative context filename from the resolved project directory, persists the structured evidence in terminal data and `WorkRunSummary`, and projects file/heading/repair/checkpoint/disposition details to Cockpit. When no unchecked task remains: `buildFinalizerHandoff` → `runFinalizerHandoff`; its hard merge gate independently runs every product `validationCommands` entry from a freshly boundary-validated `validationCwd` with `WORK_RUN_GATE_COMMAND_TIMEOUT_MS`, persists its green receipt, then merges only while the base-branch lock still holds.

**Validation isolation and closeout selection:** `validationCwd` is optional product config, defaults to the repository root, and is accepted only when its real directory remains inside the current worktree; absolute paths, parent traversal, missing/non-directory targets, and symlink escapes fail closed. Product-controlled validation receives only basic toolchain environment plus its worktree-derived cache; Rune/integration secrets are absent. On macOS, Seatbelt denies external networking but permits localhost for test servers. Compatible related-test confirmation does not relax that launch: the child receives the same outer Seatbelt and secret-free environment. The launcher alone injects the reserved, versioned marker described above; marked Rune-owned helpers retain Git-driver rejection, credential stripping, and network policy when omitting only their nested Seatbelt. Timeout reports use `validation-report-bootstrap.cjs`: report flags reach npm/npx's direct runner, then are removed before Next/Vitest worker creation. For `vitest-related` closeout, filenames beginning `-` are prefixed with `./` because the subcommand has no `--` terminator; deletions and global package/lock/compiler/test/build/loader configuration changes instead run the product's full validation commands. The legacy `runValidationCommands([])` pass contract remains unchanged; fail-closed emptiness enforcement belongs to orchestrated task admission.

**Restart resumability (durable cursor + salvage):** immediately after task selection and before any QA/coder mutation, the orchestrator requires a clean worktree, captures a verified `git write-tree` OID, and fail-closed persists `{taskId, treeOid}` as optional `OrchestrationRunCursor.taskBase` alongside non-null `currentTaskId`. A capture or cursor-write failure preserves the worktree and holds the run; unlike the old best-effort task-start checkpoint, Rune cannot proceed without the baseline that makes later review trustworthy. Role calls layer the current execution checkpoint onto this cursor, and the post-coder coordinator layers its versioned review batch. Reviewer coder rounds, role-created commits, and closeout-repair re-runs reuse the same base; a restart inside a review wave may reuse only completed verdicts whose task/base/current/hash/role-set identity still matches. Successful closeout writes the between-task cursor with `currentTaskId:null`, no execution/review checkpoint, and no `taskBase`, so the next task captures anew. Optional fields keep historical cursor JSON readable.

Recovery always reconstructs position from `tasks.md` plus task records and verifies cursor/task agreement. An interrupted cursor with a durable `taskBase` must resolve that exact tree object; it is never replaced with a tree from the mutated recovery worktree. An in-progress task reconstructs the workflow from the review batch only when its canonical identity matches; running review attempts become typed `interrupted` failures, completed normalized verdicts survive, accumulated handoffs/test-intent repair/adjudication audit state is restored, and only eligible paths with remaining budget relaunch on their durable retry binding. Drift or invalid/missing resume context fails closed. Post-role validation evidence is never recovered as reusable authorization: after a resumed quorum clears, full validation runs fresh. For a legacy interrupted-task cursor lacking the field, recovery may derive the base only from the verified commit of the latest preceding successful closeout record, then persists the upgraded cursor before redispatch. If there is no authoritative preceding closeout commit, the commit/tree cannot be verified, or the upgraded cursor cannot be persisted, recovery fails closed and leaves the worktree preserved. A legacy between-task cursor may proceed normally and capture a new clean base after selection. **Restart salvage:** recovery redispatch (`orchestrated-work-runner.ts`'s apply-loop recovery branch—the funnel for both boot recovery and cockpit `POST /api/work-runs/:id/recover`) reuses the interrupted worktree; dirty work is best-effort WIP-committed (`rune(<product>): WIP — restart salvage — <project>`, via `commitWorktreeWip`) before orchestration resumes. Advancing `HEAD` does not redefine the durable task base, so the re-run's full-task tree-to-tree artifact still includes the salvaged earlier work.

**Shutdown park:** `shutdown()` (`src/index.ts`) arms the mutation-pipeline suppression above, then after children are dead calls `parkInFlightOrchestratedRuns()` (`orchestrated-work-runner.ts`) for each active running orchestrated run with source `shutdown` (irrevocable); if a resumable cursor exists, leave it `running` so boot recovery auto-resumes it as today (parking would degrade a routine restart to a human-gated release); if there is no cursor (for example, the narrow window before first task-base persistence), resolve the deterministic branch/worktree, skip if the worktree is missing, best-effort WIP-commit a dirty tree, then write a `completed`+`parked:true` terminal + blocked-on-human supervision row—visible and releasable in approvals after restart via the standard release path. Operator-triggered active-run recovery likewise tags the old invocation's cancellation source `recovery`, so verified task output cannot supersede the ownership handoff. The applier's own `finally` skips `destroyWorktree` while shutdown is in progress, and `persistTerminalMutationState` no-ops, so nothing races the parker's writes. Composes with boot recovery: resumable runs still auto-resume next boot; only non-resumable runs are parked. The fail-closed task-base checkpoint now covers virtually every in-flight task, making this parker a narrow pre-selection fallback rather than a substitute baseline.

**Single task workflow** (`team-task-workflow.ts`): one task through role gates in order—reviewer-independence resolution (unavailable is one failed path, never coder fallback) → QA-first (tests or no-code-test rationale) → tech-lead test review (on first rejection the tech-lead **repairs** the tests itself instead of bouncing to the same QA blind spot: worktree patch guarded to `*.test.ts(x)` paths only via a pre-repair `git write-tree` snapshot delta with on-disk revert of violations, confirm-red against the product `validationCommands`—green/timeout rolls the patch back—then re-review; `repairable:false` or any repair failure degrades to the QA bounce ≤ cap) → bounded coder round → coder self-review → canonical full-task review capture → concurrent durable reviewer/tech-lead/conditional-security quorum plus conditional required designer → split adjudication when eligible → PM cap acceptance when eligible → `TaskEvidence`. Coder implementation and self-review prompts require focused checks for touched behavior and present the configured commands only as selection context; neither asks the model to execute the complete suite, which belongs to Rune's post-role stage. **Self-review is a worktree-editing coder pass with a separate terminal artifact, not aggregate model output** (`coder-self-review` stage on the coder's own model binding, through the same `runExecutionAgent` chokepoint as the implementation pass, in a fresh child process): it may edit the same files and run focused checks, and returns only a `coder-self-review` fence carrying `{outcome, notes}`. The provider-aware extractor first requires exactly one terminal whole-message candidate; only that transient text reaches the strict parser, which rejects an unknown outcome, extra fields, empty or over-long notes, and any diff/patch content. It runs after **every** implementation round, including rounds prompted by reviewer feedback. `git write-tree` snapshots taken before and after each attempt adjudicate the claim: `confirmed` must leave the tree unchanged and `revised` must change it, and the post snapshot is taken even when the executor fails or is cancelled so edits from a failed pass fail the task instead of being quietly reviewed. Extraction or parser failure with an unchanged tree gets one fresh self-review-only retry and fresh checkpoint; the implementation is never repeated. Once that retry begins, a provider/checkpoint/executor failure remains a typed `artifact-contract` exhaustion with both attempt records preserved instead of replacing the first contract failure. A changed tree or cancellation retains the corresponding `worktree-changed` or `cancelled` disposition. Each failed attempt records its own checkpoint-derived start, actual end, and actual retry decision. Successful reviews and failures retain bounded scrubbed attempt metadata in task records and transcript activity; raw artifacts remain transient.

`captureCanonicalReviewState` stages tracked and untracked work, writes `currentReviewTree`, and derives the complete diff/hash/changed paths from the cursor's stable `taskBaseTree`, so earlier coder changes remain visible after role-created commits advance `HEAD`. Reviewer, tech lead, and conditional designer/security roles receive matching base/current/hash identities; QA's authority ends after authoring tests and the tech-lead test-intent gate, so it does not receive or judge the implementation artifact. On a `revised` outcome the bounded scrubbed notes join the coder handoff notes so downstream roles see what the review changed and why. Once captured, the identities, self-review artifact attempts, and typed quorum projection remain on terminal `TaskEvidence` and flow into `TaskRunRecord` even if a later verdict is malformed or another post-capture gate fails; typed execution/quorum failures are also copied into failed records. This preserves bounded restart/Cockpit evidence while keeping raw diffs and terminal artifacts transient. Closeout re-captures against the same base after mechanical validation and requires both hash and current tree to match. Reviewer + tech lead sanction any test deleted/weakened in the artifact against the coder's and self-review's `TEST-REMOVED` handoff-note justifications.

**Terminal truth + worktree disposition:** orchestrated terminals persist two separate records. `trigger` is the immutable cause (`success`, `failure`, or `cancellation`) with its scrubbed reason and optional execution-failure/cancellation source. `disposition` is the later cleanup result (`removed`, `preserved`, or `parked`) with its reason and optional WIP SHA. Dirty worktrees and cleanup uncertainty can park a run, but never replace its trigger: executor/orchestration failures and user cancellation remain failed after WIP preservation; shutdown/recovery/other system cancellations retain their source; a genuinely successful run remains a success even when cleanup uncertainty preserves it. Late work-product normalization is forbidden from upgrading a failure/cancellation trigger to completion.

The trigger drives terminal event kind, summary outcome/exit facts/reason, descriptor error, and operator notification; disposition only controls preservation and supervision (`parked` still means `blocked-on-human`). Execution failures, context-transform operational holds, and related-test compatible-confirmation holds persist failed terminal truth even when their disposition preserves the worktree. User cancellation persists `exitCode:1` + `exitFact:'user-cancel'`. Non-user cancellation persists `exitCode:null` plus `exitFact:'system-cancel'`; its outcome still classifies the preserved work product rather than masquerading as an executor failure. `TerminalizationCoordinator` resolves disposition before any mutation/supervision terminal persistence. The finalizer's transcript hook calls non-closing `TranscriptSink.flush()`, then the outer terminal path appends the bounded `terminal-facts` row, calls `finish()`, writes the final summary, and only then persists/yields the terminal. The existing top-level `reason`, `parked`, preservation flags, cancellation correlation, related-test aggregate, and singular compatibility projection remain backward-compatible; summary and cursor readers accept historical records without newer fields. A summary carrying `contextFailure` is stricter because that record is not historical: the reader requires failed outcome, failure trigger, execution-failure exit facts, preserved disposition, and exact agreement—including absence—between the checkpoint SHA and disposition SHA. Cockpit projections/cards expose the disposition, WIP SHA, structured context repair evidence, and latest related-test confirmation state; authenticated run-detail diagnostics include the task-attributed records, Telegram's parked message renders the trigger cause separately from the preservation reason/SHA, and a related-test host-conflict hold receives explicit operational wording.

**Nested role cancellation:** every tech-lead, QA, coder, and reviewer model invocation is registered as a product-scoped `kind:'agent'` cancellable operation regardless of Claude/Codex provider (judgment calls through `team-task-deps.ts`; worktree executions through `execution-agent.ts`). The project orchestrator maps Telegram/cockpit sources to user-cancel and internal to system-cancel before closeout, so the task checkbox stays untouched. The runner emits a direct reason such as `tech-lead cancelled from cockpit (operation abc12345)` without blocker/model-failure wording and persists the scrubbed correlation in `WorkRunSummary`; user cancellation retains a failed/user-cancel trigger, while internal/shutdown/recovery cancellation retains a system-cancel trigger even if its worktree is parked.

**Planning flow:** `/plan` is PM-led scoping: the PM conducts the interview directly and emits the PM spec; there is no separate Planner step or planning-brief intermediary. Metrics reset on daemon restart. | The metrics tool is itself instrumented; if any tool call exceeds `RUNE_MCP_TOOL_TIMEOUT_MS`, the caller receives `isError:true` text `Tool timed out after <ms>ms`, and both `errors` and `timeouts` increment. A thrown handler increments `errors` and propagates through the SDK. |

**Health/workout tool contract (`HEALTH_TOOLS`, MCP health expansion):** every handler lives in a config-free PURE module under `src/mcp/tools/` (deps-injected via a `*-deps.ts` production binding, loaded lazily so building the MCP server never forces a config load) and never throws — every failure path resolves to an `isError:true` text result. `generate_workout` is the first AGENT-SPAWNING MCP tool: it calls the shared `generateWorkout()` pipeline (`src/health/workout-generation.ts`, extracted from the Telegram `/workout` command) via `runAgent('workout-generator', …)` with `userVisible:false` and a 210s agent timeout — chosen to leave headroom under the tool's 240s `TOOL_TIMEOUT_OVERRIDES_MS` wrapper timeout, so the agent's own timeout error surfaces instead of an opaque wrapper timeout. The three write tools (`log_workout_done`, `log_meal`, `update_workout_plan`) each commit-per-write via `gitCommitAndPushOrThrow` (`src/vault/git.ts`) — a write that lands on disk but fails to commit surfaces as `isError:true` with an explicit "not yet durable" message, never a phantom success.

**MCP watchdog (MCP monitoring redesign):** runs in the MAIN process (the daemon has no Telegram/scheduler) — `src/jobs/mcp-watchdog-runner.ts` starts a 60s-tick `setInterval` (`startMcpWatchdog(bus)`, wired in `src/index.ts` after `startStallCheck`; torn down in shutdown) that probes the daemon's `/health` (2s timeout; any HTTP response counts as reachable, a non-`ok` `status` is handled by the degraded rule), reads the trailing ~15-minute `deltaSeries` window from the metrics-history JSONL, and calls the pure rule core `evaluateMcpWatchdog` (`src/jobs/mcp-watchdog.ts`). Alert kinds: `daemon-down` (2+ consecutive unreachable ticks), `daemon-degraded` (3+ consecutive reachable-but-not-`ok` ticks), `error-spike` (≥5 errors AND ≥25% error rate in the window), `tool-failures` (≥3 errors for one tool in the window). Each alert key has a 6h re-notification cooldown (`NOTIFY_COOLDOWN_MS`) while it persists, and emits a one-time `✅ recovered: …` notice (with the cooldown entry deleted so an immediate re-fire re-alerts right away) when the condition stops firing. State (streak counters, active alerts, per-key cooldowns — NOT an event history) persists to `config.MCP_WATCHDOG_STATE_FILE` (`mcp-watchdog-store.ts`, tolerant load: missing/corrupt/wrong-shape → `defaultWatchdogState()`; fail-safe save: errors logged, never thrown). Notifications publish to the Telegram bus, defensively scrubbed via `scrubAbsolutePaths` even though alert texts are built path-free. The whole tick is wrapped in try/catch so a probe bug or store failure can never crash the process.

**Cockpit MCP monitoring (MCP monitoring redesign):** `GET /api/mcp/monitoring` (`handleApiMcpMonitoring`, `src/server/webview.ts`) is the single composed payload the redesigned monitoring tab renders. Every section degrades independently on its own failure — live tool snapshot (`mcp_metrics_snapshot` via the existing daemon-call machinery), daemon `/health` body, registered OAuth clients (display fields only — `clientId`/`clientName`/`createdAt`, NEVER tokens/secrets/redirectUris), file-backed history rollups (`composeMcpMonitoringHistory`, 60s in-process cache; 14-day daily + 24h hourly + 24h per-tool via `mcp-metrics-history-read.ts`), Rune-side run metrics (`readRuneRunMetrics`, `src/server/rune-run-metrics.ts` — previously defined but unwired; now wired with real `config.SUPERVISED_RUNS_FILE`/`config.WORK_RUNS_INDEX_FILE`), and active watchdog alerts (tolerant read of `config.MCP_WATCHDOG_STATE_FILE`, scrubbed before surfacing). The endpoint ALWAYS answers 200; any section failure flips `status` to `'degraded'` with a scrubbed `error` string rather than failing the whole response. The legacy `GET /api/mcp/tools/mcp_metrics_snapshot` endpoint is unchanged. The cockpit product-deep-view monitoring tab (`renderMonitoring`, `src/server/static/product-deep-view.js`) was rebuilt around this payload: KPI tiles with sparklines, a calls/errors bar chart, per-tool table, sessions/OAuth-clients list, and an alerts banner (`src/server/static/monitoring-charts.js` — pure NaN-safe inline-SVG builders: `renderSparkline`, `renderBarChart`; every color rides a CSS variable so charts inherit the app theme). The Home pill (`renderMcpMonitoring`, `home-view.js`) now shows uptime + session count + an `alert` status variant with the active alert kinds when `alerts.count > 0`. Cockpit poll interval widened from 1s to 5s (the file-backed sections only change once a minute; a 1s poll bought nothing).

**MCP daemon launchd runbook:** the committed LaunchAgent is `launchd/com.jarvis.rune-mcp.plist`, installed as `~/Library/LaunchAgents/com.jarvis.rune-mcp.plist` by `scripts/install-rune-mcp-launchd.sh`. It runs with `Label=com.jarvis.rune-mcp`, `WorkingDirectory=/Users/jarvis/workspace/rune`, and `ProgramArguments=/usr/bin/env npm run mcp:start`; the package script expands to `NODE_ENV=production node --env-file-if-exists=.env.local --import ./scripts/register-ts.mjs src/mcp/daemon.ts`, so daemon env comes from that working directory's `.env.local` when present. Required live-use expectation: set `RUNE_MCP_SECRET`; set `RUNE_MCP_ISSUER_URL` to the final public Funnel HTTPS origin; optionally override `RUNE_MCP_OAUTH_STORE_FILE`, `RUNE_MCP_HOST`, and `RUNE_MCP_PORT` (defaults: `logs/rune-mcp-oauth-store.json`, `127.0.0.1`, `3848`). The plist sets only `PATH`; it does not inline secrets. Stdout/stderr go to `~/Library/Logs/rune/rune-mcp.out.log` and `~/Library/Logs/rune/rune-mcp.err.log`; the daemon `/health` response also points at the in-repo process log.

```bash
scripts/install-rune-mcp-launchd.sh lint
scripts/install-rune-mcp-launchd.sh install
scripts/install-rune-mcp-launchd.sh restart
scripts/install-rune-mcp-launchd.sh uninstall

launchctl print gui/$(id -u)/com.jarvis.rune-mcp
launchctl kickstart -k gui/$(id -u)/com.jarvis.rune-mcp
launchctl bootout gui/$(id -u)/com.jarvis.rune-mcp
```

The install script creates `~/Library/LaunchAgents` and `~/Library/Logs/rune`, lints the source and installed plist, bootouts any existing `com.jarvis.rune-mcp` job, bootstraps the installed plist into `gui/$(id -u)`, then kickstarts it. `restart` is a kickstart only; `uninstall` bootouts the job and removes the installed plist.

Tailscale Funnel is the public Claude App ingress. Keep the daemon bound to loopback and map the Funnel HTTPS listener to the daemon:

```bash
tailscale funnel --bg --https=443 http://127.0.0.1:3848
tailscale funnel status
```

The resulting `https://<machine>.<tailnet>.ts.net` hostname is a human provisioning prerequisite, not a build artifact. Put that exact origin, with no trailing path, in `RUNE_MCP_ISSUER_URL`; Claude App then reaches `https://<machine>.<tailnet>.ts.net/mcp` while the daemon still listens locally on `127.0.0.1:3848`.

## Cockpit view

`buildCockpitView(registry, runStatus, taskProgress?, workRuns?, backlogCounts?, dispatchModes?)` (`src/intent/cockpit.ts`) is a pure projection. `CockpitProject` carries `lifecycleStatus`, `runStatus`, `actions`, and optional `progress` (gen-eval-loop block), `taskProgress` (done/total), `workRun` (id, outcome, reason, last-N output, startedAt, transcriptUrl, optional bounded pre-closeout validation evidence), `dispatchMode`+`fallbackReason`. `CockpitProduct` carries optional `backlogCounts` (product-name-keyed, repo-backed only). The cockpit filters out lifecycle-`done` projects per product (keeping every product header). `handleApiCockpit` (`webview.ts`) feeds live `RunStatusByProject` from `readCockpitRunStatus(SUPERVISED_RUNS_FILE)` + `readWorkRunProjections` (passing the supervision store's running/blocked-on-human runs as the 4th `activeRuns` arg so a live run's card renders immediately). Product run history renders the pre-closeout duration and reused/fallback state, includes only a typed invalidation code and the first 12 receipt-ID characters, and keeps this separate from the independent merge-gate result.

**Webview UX:** the cockpit sidebar polls `GET /api/cockpit` and renders products/projects with lifecycle status, run-status, per-project action buttons (start / continue / enter-planning-mode), the in-flight gen-eval-loop progress block, a static task-progress bar, and a per-project work-run block (`renderWorkRun` — active run shows elapsed + last-N output inline; terminated run shows typed outcome + reason + transcript link). The backlog drawer (`#backlog-drawer`) opens from a product's count line, fetches `GET /api/backlog/:product`, renders Bugs/Ideas tabs each with a Plan button + a `+` add chip. The Pending Approvals panel polls `GET /api/approvals`. A production-only "↻ Restart server" button posts to `POST /api/server/restart`.
