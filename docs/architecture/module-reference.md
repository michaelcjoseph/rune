# Module Reference

Per-file reference for every `src/` module, plus root tooling config, `cli/`, `scripts/`, and `policies/`. This is the deep detail extracted from `CLAUDE.md` — read it on demand when working in a given area. `CLAUDE.md` carries only the area-level module map; the per-file annotations and project-phase history live here.

The annotations preserve implementation invariants and the project-phase forensics ("project 13 Phase 1c", "project 15 P0.4", etc.) that explain *why* a given seam exists. Security/durability invariants that any change must preserve are also summarized in `CLAUDE.md` → Key Conventions → Invariants.

## Entry point & config

- **`src/index.ts`** — Entry point: validates the full operator environment via `assertOperatorConfig()` before boot side effects, then boots HTTP server, Telegram bot, scheduler. Startup sequence: `reconcileOrphans()` → `await runRecoveryFinalize()` (project 15 P0.4 — drives stale `running` supervised runs to a real terminal state through the hold-mode finalizer, classified on work product, while their worktrees still exist; awaited BEFORE the sweep) → `recoverSupervisedRuns()` (fallback: flips any run that couldn't be finalized `running` → `unknown`, fail-safe) → `restorePlanningSessions()` (reload persisted planning sessions, fail-safe) → `await cleanupOrphanWorktrees()` (startup-gated before Telegram polling, HTTP/server, and scheduler dispatch surfaces) → `runWorkRunGc()` (fire-and-forget — prunes `logs/work-runs/` artifacts over retention caps). Calls `startStallCheck(bus)`, `startMcpWatchdog(bus)` (MCP monitoring redesign), and `startPlanningExpiry()` after `startScheduler()`; `stopStallCheck()`, `stopMcpWatchdog()`, and `stopPlanningExpiry()` in shutdown. `persistPlanningSessions()` called on clean shutdown and uncaughtException paths. Does not mount `/mcp`; the Claude App connector lives in the standalone MCP daemon. Registers all mutation appliers. `shutdown()` (shutdown-park): re-entrancy guard (`shuttingDown`); arms `setMutationShutdownInProgress(true)` immediately after logging, BEFORE `killActiveProcesses()`, so a SIGTERM'd orchestrated-work child can't clobber a boot-resumable run; after `waitForActiveProcesses()` (children dead → worktrees stable) awaits `parkInFlightOrchestratedRuns()` and logs the `{parked, resumable, skipped}` summary — best-effort, a parker throw is caught and never blocks shutdown.
  Boot-time orchestrated recovery now delegates all eligibility checking to `preflightOrchestratedRecovery` before redispatch; non-resumable entries continue into orphan reconciliation instead of receiving a bespoke startup-only decision.
- **`src/config.ts`** — Typed env vars and constants. Telegram operator credentials are lazy getters so scoped MCP subprocesses can import shared modules without dummy credentials; `assertOperatorConfig()` eagerly validates them (and `VAULT_DIR`) for the main Rune process and rejects the validation launcher's reserved compatible-mode marker in an operator environment. `PRODUCT_CHAT_FALLBACK_ROOT` reads `RUNE_PRODUCT_CHAT_FALLBACK_ROOT` and defaults to `~/.rune/product-chat-workspaces`, separate from the broad autonomous-work workspace.
- **`src/cancellation.ts`** — Provider-neutral cancellation domain types shared by live transport tracking, model executors, team workflow, and durable work-run storage: `CancellationSource` (`telegram`/`cockpit`/`internal`) and `OperationCancellation` (`operationId`, source, request timestamp).

## `src/ai/`

- **`chat.ts`** — Provider-neutral conversational adapter: resolves the selected alias through `model-policy.json`, then calls the Claude or Codex primitive with the common chat system prompt, voice, scope/cwd, environment, explicit `ChatAuthority`, operation metadata, and authority-specific provider isolation. `ChatRequest` is a discriminated union: read-only forbids a writable root; both writable authorities require product, cwd, and writable root. Resolved product chats receive the dedicated strict MCP registration from `product-chat-mcp.ts`; fallback Claude receives a strict empty MCP config; fallback Codex ignores user config and `.rules`, replaces `mcp_servers` with `{}`, disables hooks/apps/remote plugins and network access, and excludes configured/temp extra writable roots. Claude conversations retain CLI session ids; Codex conversations opt into persistent threads and resume only with a non-empty thread id whose persisted authority, effective cwd, and scoped root exactly match. The three authorities map to `read-only`, `workspace-write`, and `danger-full-access`, and that sandbox selection is passed on fresh and resumed turns. Explicit legacy `writeEnabled` metadata is normalized without granting fallback workspace authority; metadata-less or threadless Codex executors rotate with bounded transcript replay. Every Codex chat gets the secret-scrubbed chat environment; a failed first turn removes its newly-created rollout via `cleanupCodexThread`.
- **`chat-turn-lock.ts`** — Keyed promise queue for complete provider-neutral turns. Serializes one transport/user/scope conversation from session read through model call and persistence while distinct users/transports/products remain concurrent; a rejected turn does not poison the queue.
- **`codex-sessions.ts`** — Best-effort Codex rollout cleanup on provider switch, session deletion, or failed first turn. Validates the thread id before scanning `$CODEX_HOME/sessions`, deletes only matching filenames, and never lets cleanup failure break `/fresh` or `/clear`.
- **`isolated-mcp-config.ts`** — Shared encoder for one isolated stdio MCP registration. Produces Claude's strict inline config and Codex's required replacement `mcp_servers` table from the same command/environment/tool allowlist/timeouts, keeping product-chat and artifact-role provider posture equivalent. Fails closed on a blank server/command/tool name, an empty allowlist, or a non-positive/non-finite timeout before either provider is spawned.
- **`product-chat-commit.ts`** — Durable resolved-product commit contract: detects only direct commit imperatives — the text is split into clauses and each tested for an optional lead-in, an optional `git`, the bare verb `commit`, and an allowlisted object, so prose that merely opens with the word ("commit message needs work") is rejected while a directive after a preamble ("looks good, commit it") is accepted; a bare affirmative with no commit language is deliberately not inferred. Captures a full pre-turn `HEAD`, and verifies a new descendant commit with valid metadata plus a clean porcelain-v1 worktree after provider completion. Its Git child is bounded and receives only basic locale/toolchain variables with credential prompting/system config disabled; surfaced failure reasons are bounded, secret-redacted, and path-scrubbed. Renders deterministic confirmed/unconfirmed receipts and accepts nullable provider prose for tool-only turns.
- **`product-chat-mcp.ts`** — Builds the isolated product-chat MCP registration through `isolated-mcp-config.ts`. Validates the product slug, launches the dedicated stdio entry with a small explicit non-secret environment carrying server-owned `RUNE_PRODUCT_CHAT_PRODUCT`, and pins the exact seven-tool allowlist. Applied on fresh and resumed configured product turns; Home/global and unresolved products do not use it.
- **`bounded-process.ts`** — Shared hardened bounded-child primitive for AI adapters. It runs a detached process group, retains only bounded stdout/stderr tails for adapter-local parsing, registers the leader with Rune's active-process supervisor, and on timeout sends group-level SIGTERM followed by unconditional SIGKILL after a short grace even if the leader exits first. The direct child is awaited/unregistered before resolution; adapters must translate output into stable failure codes rather than surface it.
- **`claude.ts`** — All Claude CLI spawning: `askClaude`, `runAgent`, `summarizeSession`. Exports `setBus(bus)` (called from index.ts so user-visible `runAgent()` calls can emit `BusAgentEvent` frames; type-only `NotificationBus` import avoids circular dep). `ClaudeResult` carries optional structured `OperationCancellation`; `execClaude` captures it before unregistering on both child `close` and `error`, so a cancellation/error race cannot erase attribution. `runAgent()` appends `{agent, startedAt, durationMs, status}` to `logs/agent-runs.jsonl` after each invocation; its `userVisible=false` path does not read `TELEGRAM_USER_ID`, emit operator bus frames, or register an operator-visible in-flight op, so scoped/background subprocesses need no fabricated Telegram identity. Exports `CLAUDE_BIN` (resolved binary path), `registerActiveProcess`/`unregisterActiveProcess` (for external spawners like work-runner), and the product-chat environment builder reused by the chat adapter. Executor preflight also enters through this AI boundary: `probeClaudeAuthentication` parses `claude auth status --json`, while `probeClaudeModelCall` invokes the exact resolved alias with safe mode, slash commands and built-in tools disabled, strict empty MCP config, and no session persistence. Both use `bounded-process.ts` and return only stable result codes; raw CLI output remains adapter-local. `runAgent()` resolves each agent's model through the model selection policy (`src/intent/model-policy.ts`) — pin → role-default → global-fallback. Also accepts an optional `writeScope?: AgentWriteScope` (`{cwd, writableDirs}`) threaded into `execClaude` — overrides the default vault cwd and adds each `writableDir` via `--add-dir` so an agent (e.g. project-setup-writer scaffolding into a target product repo) gets real write access there; omitted = legacy vault-cwd behavior. The four entry points (`askClaude`, `askClaudeOneShot`, `runAgent`, `askClaudeWithContext`) each accept an optional `voice` flag (default false) — when true, the writing-voice block is appended via `--append-system-prompt`. `askClaudeOneShot` additionally accepts a trailing `opts: {systemPrompt?, model?}` — systemPrompt rides `--append-system-prompt` composed BEFORE the voice block (the writer SOUL channel), model overrides `ONESHOT_MODEL`. Claude-only fallbacks remain Claude aliases even though the application chat default is Codex-backed. Agent frontmatter `tools:` semantics: a block list becomes `--allowedTools`; the inline form `tools: []` (`AgentDef.noTools`) declares an explicitly TOOL-LESS agent — the empty list rides inside the `--agents` JSON, stripping the subagent's toolset at the availability level (effective under `--dangerously-skip-permissions`), for single-pass synthesis agents like kb-query; an omitted field leaves CLI default tools.
- **`codex.ts`** — Codex CLI spawn primitive for Layer 5 multi-model dispatch and provider-aware chat: `resolveCodexPath()`, `getCodexBin()` (lazy — Rune boots without Codex installed), `isCodexAvailable()` (non-throwing probe), `isCodexLoggedIn()` (spawns `codex login status`, 10s hard timeout, reads + drains BOTH stdout and stderr — the current Codex CLI prints the "Logged in" marker to stderr with stdout empty; returns `Promise<boolean>`), `probeCodexProvider()` (combined binary + login probe, returns `ProviderAvailability`), `runCodex(prompt, opts)`. Executor preflight enters through the same boundary via `probeCodexAuthentication` and `probeCodexModelCall`: each ordinary probe copies only the effective executor's persisted `auth.json` and Codex executable into a private runtime, then runs under a generated macOS Seatbelt profile that denies host-sensitive reads and writes outside the runtime. Runtimes are allocated under a per-process `owner-<pid>` scope inside the repo-owned `CODEX_PROBE_RUNTIME_ROOT` (Codex refuses the OS temp directory), so concurrent probes in one checkout — including parallel Vitest workers — cannot observe each other's in-flight directories; `codexProbeOwnerRoot()` exposes that scope and `reapStaleCodexProbeRuntimes()` removes runtimes orphaned by a killed probe, bounded by both age and owner liveness. Exact-model calls use strict/ignored user config, empty MCP, no inherited shell environment, and official Codex feature switches to disable shell/unified execution, multi-agent, browser/computer-use, web, apps, hooks, plugins, and image tooling; any execution/MCP/web event is rejected. Raw JSONL and login output are parsed locally and reduced to stable codes before returning. Types `RunCodexOpts` + `CodexResult` + `CodexSandboxMode` + `ProviderAvailability`; `CodexResult` optionally returns the shared structured cancellation record plus process-level `failureKind: 'spawn' | 'timeout' | 'executor-exit'`, so execution callers classify those outcomes without parsing diagnostic prose. Cancellation is captured before unregister on child `close` or `error`. `persistentSession` creates a resumable thread, `resumeSessionId` uses `codex exec resume`, and chat calls can register cancellable in-flight operation metadata. `sandboxMode` serializes as `-s <mode>` for fresh runs and `-c sandbox_mode="<mode>"` for resumed runs, before other config overrides and the final thread/prompt positional arguments. Existing dispatch, role, critique, and other callers remain ephemeral unless they explicitly opt in. `RunCodexOpts.env` is the sandbox seam — sandbox callers (A5.2 `dispatchToExecutor`) must pass `buildSandboxEnv()`; default `process.env` is only safe for non-sandboxed Rune-internal runs. `configOverrides` appends argv-safe `-c key=value` pairs; `strictConfig` adds `--strict-config`, `ignoreUserConfig` adds `--ignore-user-config` while leaving project config and explicit overrides active, and `ignoreRules` adds `--ignore-rules` to suppress user/project exec-policy files. The discriminated `externallySandboxed` alternative requires `sandboxProfilePath`, wraps the Codex binary in `/usr/bin/sandbox-exec -f <profile>`, emits `--dangerously-bypass-approvals-and-sandbox`, and rejects any `sandboxMode`; artifact Codex uses it so the outer profile is the only Seatbelt layer. Non-external callers cannot pass a profile path. Registers each child via `registerActiveProcess`/`unregisterActiveProcess` from claude.ts for unified graceful shutdown.
- **`tool-labels.ts`** — Friendly labels for streaming tool-use events; `formatToolUse`, `scrubPathsInText` (reused by work-run transcript adapter).

## `src/bot/`

- **`telegram.ts`** — Bot init: `createBot()` factory + `wireHandlers(bot, sender)` wires message + callback_query events after senders are ready. The callback_query handler (Phase 6 C6.2) auth-gates by `TELEGRAM_USER_ID`, acks the query, then routes composite-id payloads through `dispatchApprovalStatus` (shared with the cockpit inbox) or falls back to `dispatchText` for conversational values (slash-prefixed values are rejected to prevent inline buttons from triggering destructive commands).
- **`handlers/text.ts`** — Command routing + multi-turn conversation handler. `handleTextMessage(sender, msg)` — no direct bot dependency. Exports `dispatchText(sender, userId, text, scope?, {turnId?})` shared with webview. Default conversation turns serialize the complete session transaction through `withChatTurnLock`; `resolveChatAccess(scope)` selects authority, cwd/root, validated prompt context, and a compositionally built tool surface as one invariant before the provider-neutral adapter is called and its executor binding persisted. Home/global uses `read-only` plus conversation/KB tools; unknown products and products with a missing, malformed, or escaping repo/scope use `product-workspace-write`, one dedicated fallback scratch directory, and base read/edit/shell tools only; resolved products use `product-full-access`, canonical repository cwd/scoped root, and the complete product + KB + Cockpit tool surface. Only resolved-product direct commit requests enter `product-chat-commit.ts`: the baseline is captured before provider execution, unavailable baseline fails before spawn, and a receipt confirms only an advanced valid commit plus clean tree. Stable client turn IDs make provider execution idempotent by replaying stored terminal messages and terminalizing interrupted pending turns without re-execution; a turn ID returning with different request text is refused as a conflict rather than answered from the earlier turn's record, and a pending record that cannot be persisted still terminates with a bounded reply so the WS surface never receives zero frames. Raw assistant text remains in local session persistence, while every successful reply and exception is passed through `scrubAbsolutePaths` before reaching Telegram/webview. `/gpt-5.6-terra` joins the Claude model-switch commands, resetting the executor only when the provider changes. Active-planning-session check takes routing priority over the default conversation handler — free-form text routes through `routeToPlanning` → `handlePlanningTurn` when a planning session is active. `routeToPlanning` appends "— spec proposed · /approve to scaffold · /clear to abandon" footer when the planning handler returns spec-proposed status. `/approve` is wired in `dispatchText` but intentionally excluded from `SLASH_COMMAND_METADATA` (approval is an explicit gate, not resolver-inferred).
- **`handlers/url.ts`** — URL detection, fetch, content-triager agent, routing.
- **`handlers/photo.ts`** — Photo download, photo-classifier agent, routing.
- **`skill-registry.ts`** — Resolver skill registry: `SkillEntry`, `SLASH_COMMAND_METADATA`, `buildSkillRegistry`, `getSkillRegistry` (cached), `reloadSkillRegistry`.
- **`resolver.ts`** — Classify free-form TG messages against skill registry via Haiku; returns `ClassifyResult {skill, args, confidence, second_skill, second_confidence, ambiguous}`.
- **`work-run-release-callback.ts`** — Project 13 Phase 1c — Telegram release callback handler: `parseWorkRunReleaseCallback(data)` recognises `work-run-release:<id>` and `work-run-release-confirm:<id>` callback payloads; `dispatchTelegramWorkRunRelease(sender, userId, data)` delegates to the shared `requestWorkRunRelease` runtime (dirty-confirm path sets `{confirmDirty:true}`), replies with `formatReleaseRequestReply`.

## `src/transport/`

- **`sender.ts`** — `MessageSender` interface, `SendOpts` (`approval?: {prompt, options[]}`, optional stable `turnId`/`messageId`) type, `createSenders(bot, bus)` factory; subscribes tg/webview to bus `message`, `agent-event`, `mutation-event`, and `op-event`; returns `{ tg, webview, destroy }`.
- **`notification-bus.ts`** — `NotificationBus`: typed event bus with publish/on/off. `BusEvent = BusMessageEvent | BusAgentEvent | BusMutationEvent | BusOpEvent`. `BusOpEvent` has subKind `start`/`progress`/`end` with opKind `agent`/`chat`/`one-shot`/`classifier`. `BusMutationEvent.subKind` widened with `start` (project 13 Phase 1a — carries the local-operator `operatorWorktreePath`). Fault-isolates failing subscribers.
- **`mutations.ts`** — Mutation pipeline: `MutationDescriptor`/`MutationKind`/`MutationStatus` types, applier registry, `createMutation()`, `cancelMutation()`, `activeRuns` map, `setMutationBus()`. AutoApprove appliers start immediately. Hooks into supervision-store at every state transition (seed on create, flip on startApply/completed/failed/crash, throttled heartbeat on output events). `buildSupervisedRun` carries both `lastChildAliveAt` and `lastOutputAt` params — output events advance `lastOutputAt` (LLM-output signal for quiet-run nudge), keep-alive/terminal writes thread the current value through so it is never reset. `MutationDescriptor` carries optional `outcome?: WorkOutcome` + `workProduct?: WorkProductFacts` (project 11 Phase 2) — populated by `applyOutcomeToDescriptor` in startApply's terminal branch (gated on `kind === 'work-run'`) BEFORE `appendMutationLine`. `MutationEvent.kind` union includes `start` (project 13 Phase 1a) — the `startApply` loop publishes it to the bus with NO supervision side effect and does NOT copy its data onto the descriptor (the un-scrubbed `operatorWorktreePath` it carries must never reach `mutations.jsonl`). Project 13 Phase 1b + AskUserQuestion: terminal supervision flip treats work-run/orchestrated events with `data.parked === true` as a supervision override and preserves `parkedQuestion` when present. `MutationKind` includes `work-run-release`, `work-run-answer`, and `writing` (the /blog / /writing-critique applier; its events pass the `publishDerivedRunEvent` run-feed gate alongside work-run/orchestrated-work); `MutationApplier.supervised?: false` suppresses createMutation supervision seeding for control mutations. **Shutdown-park suppression:** `setMutationShutdownInProgress(v)`/`isMutationShutdownInProgress()` — armed by `index.ts`'s `shutdown()` before `killActiveProcesses()`; while set, `startApply` suppresses ALL terminal/crash persistence and heartbeat upserts, but ONLY for `orchestrated-work` mutations — a SIGTERM'd child can't flip a boot-resumable `running` mutation to failed or clobber a just-written shutdown park. Other mutation kinds keep their existing crash semantics; on-disk state for a suppressed run is owned exclusively by `parkInFlightOrchestratedRuns` and next-boot recovery. The `startApply` finally also RETAINS a suppressed run's `activeRuns` handle (normal runs delete it) — the parker snapshots `activeRuns` only after the children are dead, and a suppressed unwind that removed its handle would hide the run from the parker entirely (codex-found race, 2026-07-08).
  Recovery safety adds an ephemeral `MutationDescriptor.recoverable?` projection (never persisted), `RunHandle.settled` (resolves after the applier's `finally`), and mutually exclusive per-run lifecycle claims for recovery handoff versus terminal teardown. While a recovery claim is held, the superseded orchestrated invocation suppresses terminal/crash persistence and destructive cleanup until cancellation has fully settled and redispatch is ready.
- **`in-flight.ts`** — Shared in-flight model-op registry: `registerOp`/`unregisterOp`/`cancelOp`/`cancelMostRecentForUser`/`listOps`. `OperationCancellation` records `{operationId, source:'telegram'|'cockpit'|'internal', requestedAt}`. `cancelOp` synchronously records the first request before SIGTERM; repeats preserve the original metadata, and executors read it before unregistering the live child. 5s heartbeat ticker emits op-event:progress; `setInFlightBus(bus)` wires bus emission; cancellation overrides the reported exit status.
- **`telegram-sender.ts`** — `TelegramSender` implements `MessageSender` and formats mutation/op events. Work-run terminal summaries preserve trigger/disposition semantics and, only after strict receipt validation, append the independent merge-validation outcome, command count, and selected profiles; `profile-unavailable` is labelled as a capability operational hold. PM-acceptance alerts scrub secrets plus configured and generic host paths. Successful delivery records keep the raw chat id only in the 0600 file sink while the console copy uses `[private]`; message bodies are never logged. Malformed or absent evidence adds nothing. Park/release/question controls and the local-operator-only worktree-path exception remain unchanged.
- **`webview-sender.ts`** — `WebviewSender` implements `MessageSender`; `register(userId, ws)`, `unregister(userId, ws)`, per-user WS fan-out; terminal message frames carry optional stable turn/message identities, and `sendToSocket` replays one persisted product-chat receipt to a reconnecting socket. `onAgentEvent()`, `onMutationEvent()`, `onOpEvent()` forward bus frames to connected WS clients.
- **`approval-actions.ts`** — Phase 6 C6: transport-agnostic approval-actioning module shared between the HTTP cockpit (`POST /api/approvals/:id/{approve,reject}`) and the Telegram callback_query handler. `parseApprovalId(id)` splits a composite `<source>:<payload>` id; `dispatchApprovalStatus(id, status)` routes to per-source queue mutators and returns three-valued `ok`/`not-found`/`error` (HTTP maps `error` to 500). All writes wrapped in `safeWrite`. `blocked-on-human` Approve routes to `requestWorkRunRelease`; Reject dismisses the parked supervision row. `work-run-answer:<runId>:<optionId>` routes to `requestWorkRunAnswer`.
