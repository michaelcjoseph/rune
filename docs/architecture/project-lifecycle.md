# Project Lifecycle: `/plan` → merged

The full path a project travels from a `/plan` conversation to a branch merged onto `main` by an orchestrated `/work` run. `CLAUDE.md` carries a one-line pointer; the per-stage detail lives here. Companion docs: `subsystems.md` (mutation pipeline, supervision, gated-merge finalizer mechanics), `reviews-kb-vault.md` (planning-session routing).

Read this when you need to know **who owns a stage, who signs off on it, and what condition advances it** — e.g. debugging why a run stalled, blocked, or refused to merge.

## Models at a glance

Role→model bindings are policy-declared in `policies/model-policy.json` (`roleDefaults`). A missing policy falls back to `def.model ?? config.AGENT_MODEL` for ordinary agent execution, while the production adjudicator binding is declaration-only and fails closed.

| Role | Model / provider | How it runs |
|---|---|---|
| pm, tech-lead, reviewer, designer, security | Opus 4.8 / anthropic | judgment calls (fenced-verdict round-trips) |
| qa, coder | GPT-5.5 / openai (Codex) | artifact producers (`runExecutionAgent`) |
| neutral critique | Claude Opus **then** Codex | cross-model hardening, sequential (Codex critiques Claude's output) |

Charters load via `composeRoleContext(role, instruction)` (`src/roles/loader.ts`): `agents/<role>/SOUL.md` → system channel (authority), `agents/<role>/memory.md` + exemplars → a low-authority fenced reference in the first user turn. SOUL wins on conflict.

Three structural facts to hold onto:

- **Validation is fail-closed by task policy and declared capability** — every planned task carries `validationPolicy`. Missing/legacy metadata means `required`; only the explicit, planning-reviewed `reviewed-no-validation` value exempts a task. Every configured command also has one exact minimum capability profile. Coders run focused task checks; after eligible review quorum and any required designer gate clear the canonical tree, Rune runs the complete selected profile plan once. Its V3 receipt binds the tree, review hash, argv/cwd, profile/configuration/dependency/environment/toolchain identity, and execution facts. Closeout reuses only an exact receipt; the independent merge gate (D3) still reruns every selected shard in its integration worktree.
- **Reviewers see the complete task Git surface** — before QA or coder can mutate the worktree, Rune requires it to be clean, writes its tree, verifies the OID, and fail-closed persists that task base in the run cursor. After each self-review Rune stages tracked and untracked changes, writes the current tree, and derives the scrubbed tree-to-tree diff from the durable base. That full-task artifact—including changes already committed by an earlier role round—is the only implementation surface reviewer, tech lead, designer, and security receive; no model-returned text or moving-`HEAD` diff is a candidate. Its hash and current-tree identity are rechecked after mechanical validation.
- **Exactly one human gate** in the whole lifecycle: `/approve` (A5). Everything downstream of it is automated and adds zero approval points (project-20 invariant, asserted in tests). The manual live-release gate some project `tasks.md` files carry is a Definition-of-Done note, not a pipeline gate.

# Phase A — Planning (`/plan` → scaffolded project)

One interactive session, split around the `/approve` gate. Pre-approval is a live PM interview; post-approval is the automated `runDownstreamPlan` pipeline. Failures after A5 leave the session `approved` so `/approve` can retry without losing the spec.

Downstream order (A6→A12) is fixed: breakdown → tech-lead self-review → `pmReviewMatch` → Claude critique → Codex critique → context seed → scaffold. The critique reads forward into both the seed and the human-visible surface. The agent writes `spec.md`/`tasks.md`/`test-plan.md`/`index.md`; `tech-spec.md`, `context.md`, and `examples/<role>.md` are written deterministically by `writeRoleArtifacts`, not the agent.

The tech-lead breakdown, PM repair, both critique passes, and deterministic `tasks.md` rendering preserve each task's `validationPolicy`. Critique parsing reconciles policy by stable task ID: an existing task keeps its already-reviewed policy even if a critic tries to change it, while every critic-added task is forced to `required`. Other parsers default omitted or malformed legacy values to `required`; `tasks.md` records the policy immediately under its task checkbox so `selectNextTask` can carry it into runtime admission.

# Phase B — Dispatch & sandbox (orchestrated `/work` begins)

| # | Stage | Primary | Reviewing gate | Advance when | Anchor |
|---|---|---|---|---|---|
| B1 | Dispatch / validate / register | `orchestratedWorkApplier` (auto-approve) | `validate()` — slug valid, project dir has `spec.md`, under per-project + global concurrency caps | `{ok:true}` + not cancelled → `SupervisedRun` seeded `running` | `jobs/orchestrated-work-runner.ts`; `transport/mutations.ts` |
| B2 | Worktree from `baseSha` | `createWorktree` | preconditions (target path free, repo has HEAD); resume rebase-reconciles against `baseBranch`; project directory plus managed `spec.md`/`tasks.md`/existing `context.md` must be non-symlinks whose realpaths stay inside the worktree | `SandboxSpec` returned, project dir found, baseline tasks snapshotted | `jobs/sandbox-runtime.ts` `createWorktree`; `verifyWorktreeProvisioning` |
| B3 | Build deps + start loop | `buildOrchestrationDeps` | none (setup) | loop begins. Per-task round cap = `ORCHESTRATED_ROUND_CAP` = 3 (hard-clamped ≤4) | `orchestrated-work-runner.ts` |

The branch is `rune-work/<slug>` cut at the repo HEAD `baseSha`. Dependency provisioning keeps the fast external `node_modules` symlink for ordinary products, but direct Next.js projects receive a local copy instead so Turbopack resolves every dependency within the worktree — the copy is staged (async, via a sibling dir renamed into place) so it never blocks the event loop or leaves a half-copied tree. `orchestrated-work` and legacy `work-run` share the deterministic per-project worktree path and concurrency caps, so the same project never runs twice concurrently.

# Phase C — Per-task loop (repeats until no `- [ ]` remains)

`selectNextTask` returns the first unchecked `- [ ]` line in document order; id = slug of the task text (stable across line moves). Every unchecked line is a real task that enters the per-task role workflow; test-first behavior is handled inside C2b, where QA authors required tests before coder work.

## C1 — Task selection
`src/intent/orch-task-select.ts` `selectNextTask`, driven by the loop in `project-orchestrator.ts` `runProjectOrchestration`. Selection reads the task's adjacent `Validation policy` metadata and defaults older tasks to `required`. Before any QA/coder mutation, `captureCleanTaskBaseTree` requires an empty tracked/staged/untracked status, stages the tree, writes a verified Git tree OID, and `prepareAndPersistTaskBase` records `{taskId, treeOid}` in `OrchestrationRunCursor.taskBase`. Capture, verification, or cursor-write failure becomes a preserved operational hold; Rune never treats unexpected pre-task dirt as the new baseline. The same base survives every reviewer-driven coder round and whole-workflow closeout-repair retry. Successful closeout writes a between-task cursor with no `taskBase`, so the next task captures a fresh one.

**Operational note (on-call):** this checkpoint is fail-closed at *every* task boundary, not only the first. A transient Git or disk error mid-project therefore holds the run with reason `task-base checkpoint failed before task mutation` and waits for a human release, where earlier behavior degraded silently and kept going. This is deliberate — QA now judges the complete implementation relative to this base, so proceeding without a verified one would reintroduce the incremental-diff misjudgment the base exists to prevent. `WORK_RUNS_DIR` lives under local `logs/` (not the iCloud-synced vault), so the expected rate is very low; a recurring hold points at genuine disk or worktree trouble, not at normal contention.

The loop is bounded by `taskCount+1` so a closeout that fails to tick can't spin. Cancellation is checked before each selection and before the finalizer.

## C2 — Per-task role workflow (`src/intent/team-task-workflow.ts` `runGated`)

Before model-policy resolution, executor preflight, dependency construction, or any QA/coder call, the production runner admits the task's validation contract. A required task must have at least one parseable shell-free command, a worktree-contained real `validationCwd` (repository root by default), every referenced executable available on the launchd-safe toolchain path, and a complete valid command-profile assignment. Rune expands strict Vitest adapters into stable `isolated`, `loopback`, and `sandbox-integration` shards, then probes each selected host capability before role dispatch. Missing commands/profiles, malformed or duplicate assignments, unavailable executables/profiles, invalid/missing directories, and symlink escapes return blocked `TaskValidationFailure` evidence and append a scrubbed `task-validation-failures.jsonl` record. Only explicit `reviewed-no-validation` tasks bypass this admission; `runValidationCommands([])` retains its legacy pass behavior outside this orchestrated boundary.

After admission, the production runner resolves all role models and executes the run-scoped executor preflight before dependency construction or the first role call: executable CLIs, persisted subscription authentication from the effective product executor state, and one bounded built-in-tools-disabled live call per unique exact model binding. Claude and Codex probes stay behind their centralized AI spawn boundaries; Codex additionally uses a private auth/runtime, official execution-feature disabling, and a macOS Seatbelt sensitive-host-read denial. When artifact MCP is configured, each distinct QA/coder format is built in a temporary scratch worktree, authenticated through its generated profile/runtime, and must complete a live relay/broker MCP `initialize` + exact `tools/list` handshake before cleanup. A success is transcripted once and cached for later tasks/closeout retries in the same run. A failure is a bounded, scrubbed, typed `blocked` terminal with no raw probe output, no invoked roles, and unchanged tracked, staged, and untracked product-worktree state; failed checks are retried rather than cached. Manual/live release-gate tasks bypass this automated-executor gate.

After preflight, each role call first persists a durable execution checkpoint naming task, role, provider, CLI format, exact model, and workflow stage. The post-coder wave additionally persists a versioned `ReviewBatchState` before launch and after every role transition. A failed checkpoint write blocks before spawn; successful task closeout clears the current checkpoint and review batch, and old cursors without either optional field remain readable. Executor or unexpected role-boundary failures carry typed evidence through `TaskEvidence` (with human-readable reasons retained as compatibility summaries). These structures—not diagnostic wording—select the operational route; policy/preflight blocks, findings, ordinary gate rejection, exhausted review paths, and cancellation remain distinct.

Artifact-role execution gets at most two total fresh-process attempts. Spawn, timeout, retryable provider, and generic nonzero-exit failures may retry once after a jittered 1–2 second cancellation-aware backoff; provider adapters expose structured termination facts where available rather than treating diagnostic wording as timeout authority. A `SIGTERM`-shaped exit or code 143 counts as timeout only when Rune's own elapsed timer fired; an external/CLI-aborted termination remains cancellation or `executor-exit`, with any CLI terminal reason bounded and sanitized. Retry requires identical `git add -A` + `git write-tree` OIDs before and after the failed attempt. The snapshot covers tracked and non-ignored untracked content only—ignored files, Git metadata, and external side effects are outside this guard. A Git-visible mutation yields `worktree-changed`, preserves the partial work, and stops. Artifact-MCP/environment/config/auth/sandbox, preflight, validation, Git, cancellation, and semantic/gate failures do not use this executor retry. Eligible QA/coder retries rebuild and stop a fresh isolated artifact-MCP environment; all retries use a new model child and emit bounded attempt/retry transcript activity. If the child and MCP cleanup both fail, the child failure remains primary and the cleanup problem is retained as secondary attempt evidence; no retry follows an uncertain cleanup. Exhaustion retains both failed attempts with scrubbed diagnostics. The `coder-self-review` terminal-artifact contract has its own narrower retry below: it may rerun only self-review once after an unchanged canonical tree, never implementation.

After preflight, a single task runs through these ordered sub-gates. Verdicts emit `role-verdict` events; rejections emit `gate-rejection`. Gate identifiers are the exact strings in code.

**Test-intent repair (gate e FAIL path):** on the FIRST rejection the tech-lead patches the tests itself instead of bouncing an unfixable state back to the same QA agent (`deps.techLeadRepairTests`, production: an `execute('tech-lead')` worktree session). Mechanics are fail-safe: the repair delta is computed against a pre-repair `git write-tree` snapshot; any path outside `*.test.ts(x)` is reverted on disk (the allowlist is deliberately NOT widened to QA's diff paths — a QA stray into product source must not license a tech-lead edit of the same source); then **confirm-red** runs the same product command-profile plan — a green or timed-out run rolls the patch back (`not-repaired` → QA bounce), while a product assertion failure threads its output tail into the re-review as `Confirm-red evidence` so the tech-lead judges red-for-the-right-reason. Capability unavailability is operational, never confirm-red evidence or coder feedback. A `repairable:false` verdict (structural rework / spec ambiguity) skips the repair entirely; every internal failure degrades to the QA bounce, never a task-fatal throw. Evidence lands as `TaskEvidence.testIntentRepair`; the attempt emits a `test-repair` activity event.

**Pre-coder invariant contract:** the two calls use the repository worktree as cwd, a product-scrubbed environment, strict empty MCP, no network-capable tool, and only Claude's `Read`/`Glob`/`Grep` tools; a non-Claude binding fails closed because Rune cannot currently offer it a read/search-only executor. The validator admits at most 20 items, at most four in each of five fixed categories, 400 characters per invariant, and one or two evidence references. Every reference must name a contained repo-relative regular file and an exact anchor present in it; absolute/traversal paths, symlinks, missing files/anchors, unaccounted draft IDs, and contradictions fail closed. Accepted items are secret-redacted and host-path-scrubbed, rendered once with a SHA-256 content hash, and the exact block reaches QA, test-intent, coder/self-review, reviewer, tech-lead, designer, and security prompts. `TaskEvidence`, `TaskRunRecord`, diagnostics, and bounded hash/count activity carry accepted evidence or typed failure metadata—never raw model output. Unflagged tasks skip both calls.

**Durable review quorum:** reviewer, tech-lead, conditional designer, and conditional security start as one correlated wave over an immutable `JudgmentContext`. `ReviewBatchState` version 1 binds the batch to task ID, task-base/current tree OIDs, canonical diff hash, workflow attempt, round, exact role set, per-attempt model/provider/format, bounded verdict/failure/cancellation evidence, and the minimum workflow context needed to resume. That context preserves accumulated and coder handoff notes, test-intent repair evidence, and the adjudication audit including executed model/provider attribution, so restart does not silently discard earlier workflow facts. Restart re-captures the canonical Git surface before invoking any role: a task/tree/hash/role-set mismatch is a typed `review-surface-drift` hold; already-completed normalized verdicts are reused; a role left `running` becomes an `interrupted` operational failure and consumes that attempt. Each quorum-eligible role gets at most two attempts total. Attempt two uses an explicit valid `roleEscalations` binding (the reviewer escalation must still differ from the coder provider); without one, it freezes and reuses the prior attempt's durable model/provider/format across policy reload or restart. The coordinator passes that exact selected binding through the judgment call to the provider spawn rather than resolving it again there. Designer has no retry because it is a separate required gate. Checkpoint failure, required-designer unavailability, or exhaustion of every eligible path produces typed `ReviewQuorumFailure` rather than fabricated role rejection.

One pass or pass-with-warnings from reviewer, tech-lead, or selected security satisfies eligible quorum, but the coordinator first drains every role result that has already settled through evidence-contract finalization; any such completed objection takes precedence over a pass. After quorum, only unresolved eligible siblings are SIGTERM-cancelled (with bounded SIGKILL cleanup if needed); a still-running required designer continues. An objection or external cancellation cancels only the remaining unresolved members. The cancellation helper targets named roles without installing a whole-batch tombstone, so it cannot accidentally suppress the designer. `reviewQuorum` and `reviewQuorumFailure` are strict, bounded evidence carried through task records, terminal mutation data, summaries/reconciliation, REST/Cockpit projections, and Telegram quorum/retry/hold progress; historical records may omit them.

**Test-deletion guardrail:** reviewer and tech-lead diff review fail a diff that deletes or weakens a test unless the coder's handoff notes (threaded into both bodies as `## Coder handoff notes`) justify it — a sandbox-impossible external/live dependency or a demonstrated flake, recorded as `TEST-REMOVED: <path> — <reason>`; a test that is red because the implementation fails it may never be removed.

**Objection loop:** findings above `low` thread back as `rejectionFeedback` (+ a severity-sorted findings ledger) into the next coder round, up to 3 rounds (`ORCHESTRATED_ROUND_CAP`; hard budget 4). A reviewer-vs-tech-lead split is recorded on first sight; if the same objection survives a coder retry, the separately declared deeper-reasoning adjudicator may resolve it. Designer objections and high/critical or irreversible objections remain direct blocks; security is quorum-eligible but any completed security fail is still an objection. An admissible adjudicator fail still requires a nonblank rationale plus an evidence-complete finding and blocks normally. Invalid adjudication artifacts get one schema-correction retry against byte-identical split evidence; retry exhaustion, provider failure, or an unavailable production binding becomes typed `adjudication-output-invalid` operational failure, preserves WIP, and never creates a finding or coder feedback. At the hard cap, a PM may accept only a bounded reversible objection and must receive the canonical diff, spec, tests, actual dissent, and full ledger; its rationale is durable. Terminals: `all-low` or stagnation (severity flat ≥3 rounds, no non-reversible high/critical) → closeout; a non-reversible high/critical residue at cap → **held**; unresolved reversible feedback at cap → **block**; adjudication output failure → **failed operational hold**. Every rejection also drafts a best-effort gate-learning lesson into the counterpart role's `agents/<role>/memory.md` (never blocks the retry). There is no per-task human park — per-task terminals are machine-owned `ready-for-closeout` / `block` / `failed`.

Once canonical capture succeeds, `TaskEvidence` retains optional `taskBaseTree`, `currentReviewTree`, and `fullTaskReviewHash` metadata on every later return path—including malformed verdicts, gate rejections, cancellations, and executor failures—plus bounded quorum role/attempt status and any typed exhaustion reason. Successful mechanical validation may additionally attach a bounded V3 full-suite attestation, compact receipt, and `PreCloseoutValidationEvidence` to `TaskRunRecord`; historical records without newer optional evidence remain readable and malformed optional evidence is dropped. Raw diffs, test names/output, environment values, tool paths, and reporter paths stay transient; transcript/diagnostic surfaces contain only bounded, scrubbed identities, durations, decisions, and typed reasons.

## C3 — Trusted post-review validation (`runPreCloseoutValidation`, Rune-owned)

This stage runs only after the workflow returns `ready-for-closeout`. It executes the complete configured profile plan once against the exact role-approved canonical tree and creates a V3 candidate. Coder implementation and self-review prompts use focused checks and cannot create or suppress this evidence. Rejected role rounds never invoke the stage; every closeout-repair workflow and recovered task obtains fresh evidence.

## C4 — Closeout validation decision (`runCloseoutChecks`, Rune-owned)

This gate runs before `performCloseout`, context transformation, checkbox mutation, or a closeout commit. It recaptures the canonical review tree and complete current V3 validation identity without launching product code. `product-commands` reuses an exact all-green command batch; `vitest-related` additionally requires complete trusted Vitest lifecycle coverage. V1/V2 evidence remains readable for history but never authorizes this reuse. Missing, malformed, red, partial, cancelled, recovered/uncertain, or identity-drifted evidence invokes the existing closeout strategy with a typed bounded invalidation reason.

At Rune boot, the reporter/observer/extractor source and installed Vitest/`@vitest`/Vite runtime resolved from Rune's own module location—not the configurable product root—become the trusted adapter anchor; later validation must match it. Before dispatching each selected profile, a fixed probe proves its contract: isolated denies networking, loopback permits local bind/connect while denying external hosts, and sandbox-integration can reach its fixed Rune-owned broker. The broker alone creates top-level `sandbox-exec` children with empty environments, private roots, fixed probe programs, and bounded candidate profiles; its Unix-socket protocol accepts no arbitrary command, cwd, environment, or host path. Missing support yields typed `profile-unavailable` before the shard runs.

For an eligible command, Rune checks out the exact reviewed tree into a fresh directory through an isolated Git index, links Rune's anchored `node_modules`, and repeats cwd containment after `realpath`. It assembles the observer from boot-captured source and sends that source, output path, reporter/extractor source, selected tag filter, and a fresh capability only over anonymous stdin. Both observer and extractor execute with the reviewed cwd; the capability-free extractor evaluates at most one bounded config and returns bounded JSON. The observer admits only allowlisted declarative settings, disables ordinary config loading, forces fork workers, and installs the counts-only HMAC reporter. Observer and independently executed exact command use the same network profile; both deny the Rune trust root, while the exact command re-allows the concrete lexical/real validation worktree and the observer's reviewed materialization remains write-denied. Materialization/setup failure, observer rejection, or red/missing evidence never suppresses that configured shard. Inherited outer confinement requires a launcher-created nominal capability bound to the exact owner/profile path; the legacy environment marker is not authority for Codex's external-sandbox bypass.

Once every selected shard is green, Rune creates one V3 aggregate attestation bound to the staged Git tree, full-task review hash, validated relative cwd, complete normalized shard argv, adapter implementations, profile plan and definition fingerprint, per-profile probe/outcome evidence, command/configuration/dependency/trusted-runtime fingerprints, hashed stripped-environment and resolved-toolchain identity, timing, and execution outcome. Eligible Vitest mappings also carry aggregate discovered/completed suite/test counts (passed/failed/skipped/todo/cancelled). A canonical SHA-256 receipt ID covers the complete reusable identity. A normally exiting leader is not sufficient: Rune quiesces the whole process group and, on macOS, asynchronously scans/kills/rescans private-nonce-bearing detached descendants before reading evidence or recapturing Git identity. Wrong cwd, changed argv/selectors/profile assignments, configuration/dependency/environment/toolchain drift, unsupported config/imports, partial/malformed/oversized/unauthenticated evidence, collection errors, profile unavailability, timeout, cancellation, nonzero exit, or uncertain cleanup cannot authorize reuse; agent prose and terminal output never qualify. V1/V2 evidence remains readable for restart/history but never authorizes the V3 post-review contract.

- Before reuse, `runCloseoutChecks` recaptures the canonical task-base-to-current review tree and complete current validation identity without launching product code. It compares the candidate field by field and records a bounded invalidation code for tree, review-hash, argv, cwd, profile, configuration, dependency, environment, or toolchain drift; missing/corrupt/incomplete/cancelled/recovery-uncertain evidence and recapture failure have their own codes.
- `product-commands` (the default when absent) reuses the candidate when the exact V3 identity and every configured shard are green, including batches whose lifecycle coverage is unsupported. It records compact `full-suite-reused` provenance rather than spawning the command list again.
- `vitest-related` requires that same exact green V3 identity plus complete trusted Vitest lifecycle coverage for every expected shard. Otherwise it collects the same changed paths between the durable task-base and current staged tree, excludes deletions, normalizes/deduplicates/rebases to `validationCwd`, and runs that identical related source selection once per strict tag shard. Deletion, global-config, or oversized selections run the complete profiled command plan. The old signature-based compatible-confirmation fallback remains only for legacy/unprofiled historical paths and emits transition diagnostics; it is not used when the profile plan is complete.
- After validation/reuse passes, Rune stages and writes the tree again, re-captures against the same task base, and requires both the canonical hash and current-tree OID to equal the artifact that cleared review quorum plus any required designer gate. A post-review or validation-time mutation fails closed with durable `ReviewSurfaceFailure` base/candidate/current identities, hashes, and changed paths; raw diff content is never persisted.

Admission or red command failures append bounded, scrubbed `TaskValidationFailure` evidence with the exact command/prerequisite, selected profile, exit status or timeout, and diagnostics. Only a product assertion failure feeds its scrubbed output tail back to the coder as `GateRejectionFeedback` for up to `CLOSEOUT_REPAIR_CAP` (2) whole-workflow repair re-runs. `profile-unavailable` is an operational hold: it consumes no repair round, best-effort WIP-checkpoints, preserves the worktree, and is labelled separately in transcript, run-feed, Cockpit, and Telegram. Cancellation stops later shards and reaps the active process group; it never creates green evidence. A timeout first requests Node diagnostic reports with `SIGUSR2`, sanitizes them, and stores them with a command/head/tail artifact under `<run>/validation-diagnostics/` before process-group reap. Exhaustion best-effort WIP-commits and parks `blocked-on-human`; no context write, task tick, or closeout commit has occurred. An interrupted in-progress task reruns its workflow and validation after recovery rather than reusing an uncertain checkpoint. `PreCloseoutValidationEvidence` carries only receipt ID, duration, outcome, reuse decision, and optional typed invalidation; it round-trips through task storage, transcript/feed activity, diagnostics, terminal summary, and Cockpit. Fingerprint inputs, environment values, host paths, secrets, and raw test output are never projected.

## C5 — Mutation closeout (`project-orchestrator.ts` `performCloseout`, Rune-owned)

Only a task that passed C3 and C4 enters this ordered sequence:

1. Normalize and compute **both** the context update and checkbox tick (`markSelectedTaskComplete`, exact task text+section, stale match refused) before writing either.
2. Persist context, then the tick.
3. `commitCloseout` delegates current evidence to the extracted `commitReviewedCloseoutTree` effect — verify the prepared managed content is unchanged, write those exact `context.md`/`tasks.md` bodies to private temporary files, seed an isolated `GIT_INDEX_FILE` from the post-validation reviewed tree, hash and install only those two prepared blobs, and reject every other tree delta. Create `rune(<product>): closeout — <task>` with `git commit-tree`, compare-and-swap advance the intended branch via `git update-ref`, then refresh the shared index. Current evidence never runs mutable-index `git commit`, so late worktree or shared-index dirt cannot enter the reviewed commit; real-Git tests cover that isolation and concurrent branch-movement refusal.
4. `verifyCleanWorktree` — `git status --porcelain` empty.

The context normalization is a deterministic migration/upsert: the exact legacy `## Canonical Interfaces` heading becomes `## Interfaces & Contracts` in place with its body preserved, and absent canonical sections are appended with `_None yet._`. The resulting document must contain each of the five canonical headings exactly once. Duplicate canonical headings, duplicate legacy headings, a legacy/canonical collision, or an update body containing a managed heading is ambiguous and fails with a structured reason, canonical/conflicting headings where relevant, and a bounded proposed repair; conflict evidence retains an exact total while displaying at most ten headings. Rune never guesses how to merge competing bodies. Authoritative spec/tasks/context access shares one managed-worktree adapter: it validates the real parent/file, opens with `O_NOFOLLOW`, verifies the descriptor still matches the current contained pathname, rejects hard links, and truncates only after verification. Node does not expose `openat(2)`, so a hostile surviving process could still race an ancestor rename after verification; closeout's serialized, post-child-reap lifecycle explicitly excludes that actor.

Advance → build a `TaskRunRecord`, append `task-records.jsonl`, write resumable `cursor.json` without the now-completed role checkpoint or task base. A context-transform refusal writes neither `context.md` nor `tasks.md` and creates no closeout commit. Rune first attempts the labeled `WIP — closeout blocked` checkpoint, then emits failed terminal truth with a **preserved** operational-hold disposition—not a `blocked-on-human` finding park. The durable run summary and Cockpit surfaces carry the resolved worktree-relative context filename, heading/repair evidence, checkpoint diagnostic or WIP SHA, and preserved disposition; host paths are scrubbed. Stale-tick or a dirty post-commit worktree remains an operational **hold**.

## C6 — Advance / loop
Re-read `tasks.md`; ticked task skipped, next selected. No `- [ ]` remaining = **branch-complete** → Phase D.

| # | Stage | Primary | Gate / criteria | Advance when | Anchor |
|---|---|---|---|---|---|

| D2 | Classify + transcript flush | `runGatedMerge` | re-runs `classify()` (diff vs `baseSha` → outcome, sets `tasksRemaining`); a hold-signal terminal → operational hold, no merge | `outcome === 'branch-complete'` | `work-run-finalizer.ts` |
| D3 | **Hard merge gate** | `runGate` (under per-product base-branch lock) | first-failure-wins: validation-present → no concurrent run → **clean dry-merge** → **zero tasks remaining** → clean tree → validated `validationCwd` → capability probes → the attested launcher independently executes **every selected profile shard** in the integration worktree, each bounded by `WORK_RUN_GATE_COMMAND_TIMEOUT_MS` (default 10 min). D3 runs entirely in a **throwaway detached integration worktree** at `baseBranch` — the real `main` is byte-for-byte unchanged until the gate is green. Before merge, the finalizer requires a schema-valid green V3 receipt bound to that integration tree, its deterministic merge-gate review hash, completion time, exact profile plan/definition fingerprint, per-profile probe/outcome facts, and command/configuration/dependency/environment/toolchain fingerprints; its shard outcomes and aggregate lifecycle counts must be internally consistent. The finalizer atomically writes the receipt mode-0600 to `<run>/gate-validation.json` and rechecks cancellation inside the base-branch critical section. Assertion failure, profile unavailability, timeout, cancellation, drift, invalid/identity-free/contradictory evidence, or receipt-write failure stops at branch-complete and never merges. Profile unavailability is projected as an operational hold, separately from assertions, in terminal facts, summary, Cockpit, run-feed, and Telegram. Release uses the same gate; recovery after a recorded merge reads the durable receipt while pre-merge recovery reruns validation. Legacy V1/V2 records remain readable without receiving V3 reuse authority. Crash mid-finalize otherwise resumes off durable `PHASE_ORDER` (exactly-once merge/push/index).

# Terminal states

| State | Meaning | Trigger |
|---|---|---|
| **completed / finalized** | successful trigger; merged to `main`, project marked Done | D3 green + merge/push landed |
| **held** | branch + worktree preserved, no merge; a later Start auto-reclaims a **clean** preserved worktree (`createWorktree` removes + re-adds it), while a **dirty** one refuses with commit-or-discard guidance — uncommitted work is never auto-destroyed | non-reversible high/critical finding or merge-gate refusal; typed operational failures—including profile unavailability and structured context-transform refusal after its WIP checkpoint attempt—keep a failure trigger |
| **parked** | cleanup disposition preserves the worktree and waits for **explicit human release** (never auto-releases); it does not replace the terminal trigger | dirty/uncertain terminal cleanup; finalizer/mapping park flags; closeout repair exhaustion (WIP-committed); `PARKED_RUN_NUDGE_AFTER_MS` fires a one-time staleness nudge |
| **blocked → failed** | durable stop, task not skipped | task didn't reach closeout, or loop non-convergence |
| **failed** | hard failure | worktree-create error, orchestration throw, user cancel |

Every orchestrated terminal now stores an immutable `trigger` (`success | failure | cancellation`, with execution-failure/cancellation source where applicable) separately from its worktree `disposition` (`removed | preserved | parked`, optional WIP SHA). The runner resolves disposition before persisting terminal mutation/supervision state; the finalizer's transcript checkpoint stays open so the resolved `terminal-facts` row lands before final close and the disposition-aware summary rewrite. Summary outcome, exit facts, descriptor error, event kind, and notifications derive from the trigger; disposition affects preservation and supervision only. Executor/orchestration failure uses `exitCode:1` + `execution-failure` and remains failed after dirty-WIP parking. User cancellation uses `exitCode:1` + `user-cancel` and remains failed. System/shutdown/recovery cancellation uses `exitCode:null` + `system-cancel`, retaining work-product classification without being mistaken for an executor failure. Cleanup uncertainty after genuine success does not invent a failure, and late work-product classification cannot upgrade a failure trigger to completion. A summary carrying structured `contextFailure` is accepted only with failed outcome, a failure trigger, execution-failure exit facts, preserved disposition, and exact agreement—including absence—between the checkpoint SHA and disposition SHA. The transcript, run summary, authenticated detail/Cockpit projection, and Telegram parked message expose the same scrubbed cause plus disposition; legacy top-level reason/parked fields and readers without the optional records remain supported.

Cross-cutting supervision (`jobs/stall-check-runner.ts`, 30s tick): `checkStalledRuns` kills child-dead runs (5min); `planQuietNudges` then `planQuietCancel` handle alive-but-silent runs (keyed on `lastOutputAt`); `planMaxRuntimeKills` enforces `WORK_RUN_MAX_RUNTIME_MS` regardless of liveness (fail-toward-kill). Cancellation carries both terminal classification (`user | system`) and actuator source. User, shutdown, recovery, and unspecified system requests are irrevocable. Quiet/max-runtime requests are provisional at the post-workflow boundary only: non-ready evidence still stops, while `ready-for-closeout` atomically supersedes the active watchdog request, emits `system-cancel-superseded`, resets the quiet cycle (and max-runtime epoch when applicable), then performs normal closeout and continues. → `subsystems.md` for the supervision-store activity-reset mechanics.
